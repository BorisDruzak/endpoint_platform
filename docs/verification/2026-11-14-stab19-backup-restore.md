# STAB-19 — Восстановление Endpoint из резервной копии

14 ноября 2026 года. Изолированная репетиция на Windows 11 и PostgreSQL
16.15. `pg_dump` и `pg_restore` версии 16.16. Исходная ревизия сервера
`8275188a888a98d5ecd36dddb0de2a3420c86daa`, схема
`0052_inventory_installation`. Исходная и восстановленная базы созданы
специально для теста. Устройства, сессии, ключ и артефакт синтетические.

1. Gateway выдал разрешение на выполнение `context.health.collect`.
   Клиент сохранил результат, затем исходный API остановили.
2. `pg_dump --format=custom` создал копию БД. В комплект вошли артефакт,
   `git archive` точной ревизии серверного кода и отдельный каталог
   тестовых секретов и ключа. Манифест связывает ревизию, схему и SHA-256
   несекретных файлов. Его подпись проверена публичным ключом, полученным
   до восстановления.
3. Копию комплекта развернули в другом каталоге. `pg_restore
   --exit-on-error --single-transaction` восстановил БД в новую пустую базу.
   Из распакованного архива отдельным процессом запустили API.
4. API принял прежнюю сессию администратора и прежний bearer устройства.
   Gateway дважды подтвердил тот же результат, сохранив один результат и
   один снимок. После ACK запроса агент получил точные байты артефакта.
   Тестовый ключ из копии создал новую подпись, которую принял исходный
   публичный ключ. Проверены ревизия архива и версия схемы в восстановленной БД.

Измеренное время от начала восстановления до успешной проверки API —
**3,932–4,020 с** в двух прогонах. Это время включает создание целевой базы, копирование и
проверку комплекта, `pg_restore`, запуск нового процесса и проверку результата.
Отдельная запись, созданная после завершения копирования БД, отсутствовала
после восстановления. Между концом экспорта и записью этого маркера прошло
**0,186–0,212 с**. Это нижняя оценка интервала от снимка до контрольной записи,
а фактический RPO production зависит от частоты и давности доступной копии.

## Повтор с восстановленным worker на Linux

16 ноября репетиция выполнена на изолированном Ubuntu с PostgreSQL 16 из
серверной ревизии `55afa8511222af735263fe3f194861180e16d919`. Схема
`0053_activity_dirty_since` считана из исходной БД и включена в подписанный
манифест. API и worker запускались отдельными процессами с кодом из
распакованного архива. API использовал тот же WebSocket-бэкенд `wsproto`,
что и штатная служба.

До запуска worker синтетическая строка Activity оставалась в
восстановленной БД с исходным dirty-флагом и маркером. Worker пересчитал её,
снял dirty-флаг и очистил `dirty_since`. API прошёл проверку исходной
учётной записи администратора, прежнего удостоверения агента, выдачи
артефакта и двух ACK одного сохранённого результата. Проверка подписи,
целостности архива и запуск обоих процессов вошли в общий замер.

От начала восстановления до всех проверок прошло **4,737–4,839 с** в двух
прогонах. Созданный после экспорта маркер не восстановился. В обоих
прогонах от конца экспорта до коммита этого маркера прошло 0,075 с.
Это нижняя граница промежутка между снимком и поздней записью.

Сопутствующие испытания принудительной остановки API до записи
результата, после записи до ACK и остановки PostgreSQL завершились
за 2,148 с, 2,110 с и 0,315 с соответственно. Временные базы,
слушатели и рабочие каталоги удалены. Замеры относятся к синтетической
нагрузке и loopback на стенде.

## Запуск

```powershell
python -m pip install -r requirements-ci.txt -r requirements-server.txt
$env:ENDPOINT_TEST_POSTGRES_URL = 'postgresql://postgres@127.0.0.1:55439/postgres'
$env:ENDPOINT_TEST_POSTGRES_BIN = '<каталог pg_dump и pg_restore>'
$env:ENDPOINT_STABILITY_RESTORE = '1'
python -m pytest tests/gateway/test_stability_restore.py -s -q --disable-warnings
```

Для production предстоит получить комплект из внешнего хранилища и повторить
восстановление на изолированном Linux. При приёмке зафиксируйте время снимка и
последней подтверждённой транзакции, время получения последней пригодной
копии и время до прохождения проверок API, worker, базы и раздачи артефактов.
Сверьте фактические секреты идентичности, конфигурацию SSO, TLS и доверие
устройств, signing inputs каждого канала и точный манифест реально
развёрнутого выпуска. Доступ к закрытым ключам и резервным копиям проверяется
через их штатное защищённое хранилище. Тестовая подпись относится к комплекту
репетиции.

## Проверка доступности production-копии

14 ноября на всех трёх узлах Proxmox проверены списки backup для VM115
в `pbs`, `local` и `zfs-vm-storage`. Все девять запросов вернули
пустые списки. В расписаниях кластера VM115 не указана. Эта проверка
покрывает перечисленные хранилища.

Последний найденный локальный архив Endpoint на VM115 —
`pre-proxmox-health-5c3eb383-20261112T055211Z.dump`. PostgreSQL 16.15
прочитал оглавление из 566 записей. Размер 60 464 891 байт, SHA-256
`e71e1fc8a5245122aea1e1255bf8dcf4e9fd99a28c2dcbfd80374ad4ea7dc817`.
Время создания по оглавлению — 12 ноября, 05:52:11 UTC. Дамп лежит на
корневой файловой системе VM115. На той же VM найден локальный каталог
резервных копий конфигурации. Проверки проводились в режиме чтения.

Для проверки production-восстановления нужен внешний комплект либо
подтверждённый внешний источник, доступный со стенда восстановления.
Время создания найденного архива фиксирует давность этой локальной копии.

16 ноября в 01:28 UTC повторная проверка обнаружила тот же локальный
дамп. SHA-256 совпал, `pg_restore -l` прочитал все 566 записей
оглавления. На момент проверки архиву было 3 суток 19 часов 36 минут.
Во всех девяти сочетаниях узла и хранилища
`pve1/pve2/pve3 × pbs/local/zfs-vm-storage` список копий VM115 снова
был пуст. Два включённых задания Proxmox охватывают VM102, VM104,
VM105 и VM106. Дата проверенного локального архива показывает его
возраст, а пригодность внешней копии и фактический RPO production
остаются неизвестными.
