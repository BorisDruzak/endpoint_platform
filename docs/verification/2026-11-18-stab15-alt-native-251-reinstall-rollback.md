# STAB-15. Офлайн-переустановка ALT 3.2.251 и нативный откат до 3.2.249

Один временный клон ALT Workstation K 11.4 x86_64 из чистого снимка VM132 работал на закрытом мосту без маршрута по умолчанию. Отдельный Gateway и БД обслуживали одну вручную одобренную карточку. Штатный verifier подтвердил точные подписанные источники обоих выпусков.

## Офлайн-удаление и переустановка 3.2.251

После исходной установки 3.2.251 работали Core и Support, Gateway подтвердил ACK 1 и WSS. При отключённом виртуальном интерфейсе и недоступном TLS штатные команды `remove` и `install` каждая вернули внешний код 21 и нативный код 0. После удаления оба RPM отсутствовали. После установки оба прошли `rpm -V`. Core оставался неактивным. В журнале ожидали события удаления 2 и установки 3 при ACK 1. Совпали карточка, поколение, байты, владельцы и режимы четырёх файлов. Сохранились лабораторный origin, CA, identity и credential.

После возврата TLS обычный `reconcile` доставил оба события и получил ACK 3. Регистрация Support вернула HTTP 409. Setup вернул 21, bootstrap остался pending, `runtime-ready` отсутствовал. Core и Support были включены, но неактивны. Свежей WSS не появилось.

В этой проверке политика Support имела исходное состояние `enabled=false` по умолчанию. Диагностика после операторского восстановления и seq4 показала, что ревизия, поколение и credential исходного снимка Support при удалении отсутствуют, поэтому сравнение этих полей дало `null`. `support_rebind_until=null`. Поколение установки и credential в событиях 2/3 совпали, последний credential совпал и с текущей записью Support. До события удаления отсутствовали аудиты успешного снятия компонента и явного отключения политики. По точному коду сервера три поля снимка заполняются при событии удаления, при отсутствии подтверждённого основания seq3 не мог создать ticket. Код маршрута отдаёт безопасную причину `Support key ownership conflict`. Квитанция HTTP фиксирует код, а не тело ответа. [Семантика rebind](../runbooks/LINUX_NATIVE_SETUP.md)

## Операторское восстановление и нативный откат

Штатный reset регистрации Support для одной карточки вернул HTTP 204. Замена регистрации использовала разрешение один раз, в аудите сохранилась одна запись администратора. Политика Support осталась выключенной, туннель не открывался. Повторный reconcile вернул 0. `runtime-ready` появился, Core и Support запустились, ACK 3 сохранился. Gateway принял новую WSS 3.2.251 `82700feb-1615-4855-8507-e303f96a2fe3`.

На том же готовом клоне точный Setup из комплекта 3.2.249 с SHA-256 `8ceb7cae4b0abb112071a1af8c934b3693507a9de2a6c668d2e479d1a52e6bda` совпал с Setup внутри подписанного Core. Штатная команда `upgrade` проверила оба RPM и вернула внешний и нативный код 0. Оба RPM прошли `rpm -V` сразу и после перезагрузки. Сохранились четыре файла, карточка, поколение и ACK 4. После смены boot ID Core, Support и update path работали. Gateway принял новую WSS 3.2.249 `12d8e840-be02-47d1-abbe-bfc99d879091`. Gateway сохранил четыре события и одну карточку, OTA-назначений и отчётов не было.

VM, диск, отдельные Gateway, БД, alias и временные каталоги удалены. Исходная VM132 осталась выключенной. Квитанции в `C:/endpoint-platform-wix-build/stab15-alt251-remove-reinstall-rollback`, SHA-256 манифеста `ae465ca85e3e1cfad9530dc6e7de0be79010edea6d347050f90349cc5672f8f2`.
