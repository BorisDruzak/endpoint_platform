# ALT Linux 3.2.246 — подписанный нативный кандидат

Ветка `codex/alt-native-246`, исходник `aa23eef0ffc677d43f481789a410ee763c6d488a`.
Кандидат использует нативные Core и UserSensor RPM, встроенные Setup
3.2.246 и Support 1.0.0. Выпуск в каталоге и политика развёртывания не
создавались. Область проверки — ALT Workstation K 11.4 amd64.

## Чистая установка без сети, VM182

VM182 — полная копия снимка `inventory-alt114-p11-rpm-ready` VM132.
В конфигурации до первого запуска удалили унаследованные параметры
сети. В госте QGA подтвердил единственный loopback и ALT Workstation K
11.4 x86_64, ядро 6.12.85-6.12-alt1. До установки отсутствовали RPM
Endpoint, конфигурация и локальная квитанция, свободно 29 GiB.
`rpm -U --test` прошёл для точных подписанных пакетов. Из подписанного
Core извлечён и проверен настоящий Setup 3.2.246.

Штатный Setup установил оба RPM. Операция
`39b7ff05-da3b-442a-99d3-24c4602d3efb` зафиксировала нативный код 0,
исходник и SHA-256 обеих подписанных RPM. `rpm -V` завершился с кодом
0 и без строк диагностики. Внешний код Setup 21 соответствует
незавершённому offline bootstrap: состояние `invocation_possible`,
`settled=false`, `bootstrap=pending`, sequence 0, ACK 0, Device ID
отсутствует. Сохранена исходная квитанция. За этим прогоном остаются
открытыми реальная регистрация, WSS, UserSensor и независимый Support.
После штатной перезагрузки сменился boot ID, SHA-256 исходного журнала
остался `93392e1cee7e22483de3fe6a93d422b0dc365fbf304af866bd7e7fe4639083b7`,
повторный `rpm -V` вернул 0. VM182 штатно остановлена с сохранённым
журналом.

## Переход с подписанного 3.2.183 без сети, VM183

VM183 — полная копия снимка `inventory-alt132-pre-offline-p11` VM132.
До первого запуска удалены унаследованные параметры сети. В госте
QGA подтвердил только loopback, ALT Workstation K 11.4 amd64 и 25 GiB
свободного места. Оба 183-alt6 RPM прошли `rpm -V`. Старый журнал содержал
штатный native 0, завершённый bootstrap, событие 1 и ACK 1. Исходник
`21fc543af8d4b8b24df83f29a27e4e2eeb86c268` и SHA-256 обоих исходных RPM
совпали с [квитанцией 3.2.183](../releases/linux-3.2.183-native.json).
Исходный Device ID совпал с файлом идентичности. Core и Support были
активны. Для штатного `staging.conf` применены проверяемые параметры
staging.

Точные RPM 246 прошли проверку обеих подписей и `rpm -U --test`.
Setup 246 записал нативный 0 в операцию
`1cef9a7c-800c-4a88-9148-05b0fbf77b5b`, установил оба 246-alt6 RPM и
завершил `rpm -V` без замечаний. Сохранились Device ID, поколение, четыре
приватных файла с их правами и владельцами, а также исходная квитанция
`a2db02c5-e28f-4941-9b46-1b6d6f3b2897`. Состояние `settled=true`,
sequence 2 и ACK 1 подтверждают локально завершённый нативный переход
с ожидающей доставкой. Внешний код Setup 21 и `bootstrap=pending`
фиксируют ожидание связи. Retry timer работал, Core и Support были
включены, но ожидали доставки в неактивном состоянии.
Перезагрузка сменила boot ID. SHA-256 журнала
`88ff27d5477e1f17a9072568200f5868beb2f5bd997b1c9a785fa650c3e17480`
и времена установки обоих RPM сохранились. `rpm -V` повторно вернул 0.
VM183 штатно остановлена после повторной проверки.

## Изолированный Gateway и интерактивный UserSensor, VM184

VM184 создана из чистого снимка ALT 11.4 VM132. Сеть ограничена мостом
`vmbr144` между VM184 и VM142, без маршрута по умолчанию. На VM142
выделили отдельную БД PostgreSQL 15 со схемой
`0056_context_collection_history`, отдельные API и worker. Они работали
на source `aa23eef0ffc677d43f481789a410ee763c6d488a`. TLS проверялся по
существующему лабораторному CA и штатному имени staging. Авторизация
разрешила одно ручное использование только для 192.0.2.184/32 и
точной пары RPM. Исторические идентичности VM132/VM107 не использовались.

Штатный издатель платформы зарегистрировал строгую проверенную пару
`aa550ba9-a173-4020-834c-d111de9155b1`. После первичной установки Setup
вернул 21, пока ручная заявка `d704ce23-a8b4-4a70-809e-f5684c36817a`
ожидала. API одобрил её с HTTP 204. Штатный `reconcile` завершился с
кодом 0, журнал принял native 0, sequence 1/ACK 1 и `bootstrap=complete`.
В БД одна карточка `0c405b42-3fda-405b-969e-8db4edeee64c`, одно событие
`a5070b31-085d-4b7d-aeca-e4c5cd65c129` с ACK и свежая WSS
`d1965817-9a54-48ac-abb8-ac073d31404c` с Agent 3.2.246 linux_amd64.
В отдельный отчёт вошли и принятые сервером heartbeat.

Политику Activity без foreground/browser назначили только этой
карточке. На временном пользователе LightDM открыл реальный активный
локальный X11-сеанс. XDG запустил `--linux-user-sensor` из 3.2.246 и
`endpoint-kde-probe`. Gateway принял `READY` и сигнал UserSensor
`2026-11-17T20:53:34.046994Z` на той же карточке. Support запустился после
регистрации. Независимая SSH-сессия требует отдельного прогона.

## OTA на установленном 3.2.246

Установленный watcher отклонил исторический OTA-архив 3.2.206 без
авторизации издателя до остановки Core. Совпали PID, SHA-256 селектора и
четырёх приватных файлов. На первом запуске fixture создала родительский
каталог updates с неверными метаданными. Watcher его изолировал, затем
та же проверка выполнена на каталоге, восстановленном штатным кодом.
Диагностика обоих запусков сохранена.

Оператор подписал метаданные точного исторического архива SHA-256
`ebb77e1a8a2adb9730669e1ef16ccbfe6a781fbc0a2747b6fa0fd209d40ad504`.
Установленный watcher принял локальный pending
`439fca9a-54dd-4ee6-87c1-895ce6580e52`, записал один успешный результат
и переключил Core на 3.2.206. Gateway принял WSS
`a1323af4-6579-45a0-a178-ea67e02fc69d` на той же карточке.

Близкие запуски проверки с отказом и успешного переключения исчерпали
лимит systemd. Локальный запрос отката сохранился. Оператор выполнил
`reset-failed` и запустил штатные updater и path. Отбор 3.2.246 и его
исходной ревизии восстановился. Штатная запись селектора стала каноническим
JSON, поэтому её SHA-256 отличается от файла RPM, хотя версия и ревизия
совпали. Четыре приватных файла, целостность RPM и работа Core/watcher
подтверждены. После отката Gateway принял новую WSS
`2a76e0fa-297e-4899-8eeb-03282144d75c` для исходной карточки.
Этот прогон подал локальный запрос watcher. Канал назначения OTA через
Gateway и kill/timeout/power loss для 3.2.246 требуют своих квитанций.

После экспорта квитанций удалили три собственных клона VM182/183/184 и
изолированные API, worker, БД. Исходные VM107/132/142 и прежний лабораторный
Gateway сохранены.
