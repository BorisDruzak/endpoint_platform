# STAB-02 — потеря питания ALT 3.2.261 после записи результата

Проверен неизменённый подписанный комплект Core/UserSensor 3.2.261-alt6 для ALT Workstation K 11.4, ревизия `788fe236bba1685526c270cc0febc11c9866697f`. SHA-256 Core RPM — `018ab4d1c3abc4619c4d59cfa74da1e9655971a1876a247ca7393cde8a05f1cd`, UserSensor RPM — `f02933902e73d103af6d35d575b8502af1fa2937ffd643e33244ed6a5c3b3510`. В каждом прогоне выделенный Gateway удерживал только `result_ack` одной помеченной коллекции `health_v1`. Установка пакетов, агент и остальной транспорт штатные. Клоны и базы отдельные, контур закрытый.

## Первый прогон после свежей установки

До обрыва питания на VM221 оба `rpm -V` вернули 0. Для команды `e556963c-02ec-4cba-b338-ef98d68253c7` локальный SQLite содержал завершённый inbox и один ожидающий результат. Gateway уже записал один результат и один снимок, ACK удерживался. На новой загрузке локальная запись и SHA-256 результата сохранились побайтно. Ни новой WSS, ни доставки ACK в интервале наблюдения не было.

После загрузки оба RPM оставались зарегистрированы. Совместная проверка `rpm -V` вернула 2 и показала 161 несовпадение размера и хеша. Основной ELF Core, его unit и unit updater.path стали нулевого размера. systemd интерпретировал пустой unit Core как `masked`. Сохранились ненулевые файлы NetworkManager и SQLite. Корень был на Btrfs `/dev/sda2[/@]`, диск Proxmox local-lvm SCSI с `iothread=1` и без явного переопределения cache. Журнал этой загрузки показал Btrfs tree-log replay. В сохранённом ограниченном выводе ошибок ввода-вывода нет. Причина потери содержимого файлов не установлена.

ACK в первом прогоне не освобождался, пакеты не переустанавливались. Первичный архив `health-power-ack/initial-power-cut-hold.zip`, SHA-256 `b3c3971d2158bff1f543308a75e00fd82c3e4e3f2b6ee5fe4d68fd4234c63645`. Это незавершённое восстановление после свежей установки. Результат отдельного прогона после обычной загрузки его не отменяет.

## Отдельная проверка после обычной загрузки

В VM241 с новой БД после установки .261 выполнили штатное выключение и запуск. Перед запросом оба `rpm -V` вернули 0, Core работал с ACK 1 и свежей WSS. Для команды `96ce6e00-0ca4-4438-b723-8dca51b9d54d` до отключения питания зафиксированы завершённый inbox, одна запись ожидающего результата и один результат со снимком на Gateway. После отключения и нового запуска на той же карточке подтверждены новый boot ID и новая WSS. Пока ACK оставался удержанным, агент передал тот же сохранённый результат. У Gateway сохранились первоначальные ID коллекции, команды, результата и снимка и одна запись каждого результата и снимка.

В трассе один командный кадр и три кадра результата с одинаковым SHA-256 полезной нагрузки. После освобождения ACK для последовательности 1 новой WSS локальный outbox опустел. Прежние идентичность, установка и ACK 1 сохранились, оба RPM прошли проверку. Само выполнение пробы внутри Core отдельно не трассировали. Первичный наблюдатель завершился после освобождения ACK, потому что успешный вызов QGA без вывода не вернул поле `out-data`. Завершение подтверждено продолжением только для чтения без повторной команды или разблокировки.

Архив 23 квитанций `health-power-ack-established/established-power-cut-ack.zip`, SHA-256 `72012f11df58883c2605fb8c4652b1f4623919ac0e78879cfdca122097fe1df2`. Оба архива находятся в `C:/endpoint-platform-wix-build/stab15-alt-native-261` по указанным относительно него путям. Проверены CRC, встроенные манифесты SHA-256 и автономный `verify.py` для второго прогона.

VM221 и VM241, их диски, выделенные базы и процессы Gateway, лабораторный адрес и временные каталоги удалены. Исходный снимок VM132 сохранён.
