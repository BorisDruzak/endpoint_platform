# Лабораторный стенд Windows 11 LTSC для перехода 3.2.205 → 3.2.276

25 ноября 2026 на чистом диске VM480 установлена активированная Windows 11
Enterprise LTSC 2024 Evaluation x64 (`EnterpriseSEval`), 24H2, сборка
`26100.9457`. Стенд представляет отдельный профиль от `EnterpriseS`, который
использовался в [испытании обрыва MSI](2026-11-25-windows11-205-to-276-active-msi.md).

## Подготовка Windows

- Образ Windows получен из [Microsoft Evaluation Center](https://www.microsoft.com/en-us/evalcenter/download-windows-11-enterprise).
  Хэш ISO `67cec5865eaa037a72ddc633a717a10a2bed50778862267223ddb9c60ef5da68`.
  Установлен `EnterpriseSEval`, индекс 1. Подтверждены Secure Boot, TPM 2.0 и
  завершение OOBE. QEMU Guest Agent установлен с драйвером VirtIO Serial,
  каталог которого подписан Microsoft Windows Hardware Compatibility Publisher.
- Базовая сборка `26100.1742` содержала установленный checkpoint
  `Package_for_RollupFix~31bf3856ad364e35~amd64~~26100.1742.1.10`.
  Часы ВМ приведены к UTC. Штатная активация Microsoft вернула `LicenseStatus=1`
  и 129 600 минут оценки. Прокси и временный ограниченный канал активации
  удалены до начала обновления ОС.
- SHA-256 x64-пакета [KB5129195](https://support.microsoft.com/en-us/servicing/os/windows-11/2026/09/kb5129195-windows-11-24h2-25h2-security-update)
  `b33ff7aab5bbbbb73867f3f5c2f492fe97c0129b96aa1941bc270610d7876dfa` совпал
  с каталогом Microsoft и собранным внутри ВМ файлом из пяти частей.
  DISM завершился кодом `3010` в 18:18:55 UTC. После перезагрузки Windows
  подтвердила `KB5129195`, установленный rollup `26100.9457.1.0`, действующую
  активацию, отсутствие ожидающей перезагрузки CBS, сетевых адаптеров и
  маршрутов по умолчанию.

## Результат первого Setup 3.2.205

Setup стартовал в 18:30:56 UTC и через 80,653 с вернул `21`, стадия `MSI`,
класс `MSI_EVIDENCE_FAILED`. Windows Installer записал события `1033` и
`11707` с успехом для 3.2.205. Запрос Windows Installer по точному ProductCode
вернул `-1`. Служба Core, первый native ACK, устройство и использование
кампании отсутствовали. Защищённая запись осталась в `msi-starting`,
sequence `1`, с точным MSI в кэше.

На чистой ВМ проверка Authenticode исходного EXE вернула `UnknownError`
с сообщением о недоверенном корне. В исходнике 3.2.205 подготовка нативной
операции создаёт запись до вызова `Copy-InstallerRecoveryInputs`. Этот вызов
требует `Valid` для подписи того же EXE и прерывает сценарий при отсутствии
доверия. Событий MSI оказалось недостаточно, чтобы подтвердить итог Setup.

VM480 штатно выключена. Снимок `factory205-msi-evidence-hold` сохраняет
операцию и кэш. SHA-256 `transaction.json`
`e5369562213a3ca46652d9cdd5b65976b35de6521cbb546c1d5e00e34289a8dd`.
Повторного MSI-запуска и назначения 3.2.276 в этом опыте не было.

В коммите `e23b39e42234` проверка и копирование подписанных входов восстановления
перенесены перед нативной подготовкой в обычном Setup. Регрессионная проверка
подтвердила ошибочный порядок до правки и прошла после неё. Подписанные
артефакты 3.2.205 и 3.2.276 остались историческими входами опыта. Сетевой
переход на сборке `26100.9457` остаётся открытым.

## Повторная чистая установка на сборке 26100.1742

Установили Windows 11 Enterprise LTSC Evaluation из того же ISO на чистый
диск VM483 и активировали её штатным способом. До подключения к лабораторному
Gateway на ВМ развернули утверждённый корневой сертификат. Под `SYSTEM`
подтверждены `Valid`, ожидаемый издатель, метка времени и тот же SHA-256
Setup 3.2.205. Сеть ВМ ограничивалась отдельным мостом к Gateway.

Setup 3.2.205 на сборке `26100.1742` завершился через 266,079 с с native exit
`0` и `SERVICE_RUNNING`. Сервер принял один `installed` event и ACK1 для
точного MSI. Подтверждены одна карточка, одна активная учётная запись
устройства, WSS на Core и Foundation 3.2.205, а также готовность Observer
1.0.11. UserSensor отправил свежий образец из обычного интерактивного сеанса.
Параметры разового автоматического входа удалены.

Перед сетевым опытом сохранены снимок дисков `primary205-ack1-before276` и
контрольная копия выделенной БД с SHA-256
`4244e5ada932e2f05784c418ebc72576883c2b27b42a3c2fb13bf51427bdac63`.

## Сетевой переход 3.2.205 → 3.2.276 на сборке 26100.1742

Через Console создано одно назначение `3410f886-c13b-46ae-a151-e2675ab0940f`
на ту же карточку VM483. Оно использовало EXE и MSI 3.2.276 из таблицы выше,
связанные с исходником `4f1d5d93696b073aae0d33ce1d7880c2f4ddb24f`.
Gateway зафиксировал `applied / setup_post_restart_confirmed`.

| Переходы назначения | Время |
| --- | ---: |
| `assigned` → `downloading` | 14,449 с |
| `downloading` → `installing` | 45,856 с |
| `installing` → `verifying` | 420,281 с |
| `verifying` → `applied` | 200,672 с |
| От назначения до `applied` | 681,259 с |

Подтверждены `UPDATED / SERVICE_RUNNING / 0`, доставленный native ACK2,
точный MSI и Core 3.2.276 и сохранение четырёх приватных файлов по сводному
хэшу содержимого и ACL. Сохранились исходная загрузка Windows и обычный
интерактивный сеанс. Свежий WSS принял `health_v1` и вернул успешный результат.
Шесть измерений за 182,795 с подтвердили устойчивую работу служб, компонентов
и реальный образец UserSensor. Наибольший интервал измерения пришёлся на
`installing` → `verifying`.

Защищённые метрики Setup уточняют этот интервал. `stage-online` занял
46,098 с, три вызова `prepare` суммарно 17,668 с, `compound-finalize` —
23,057 с, `restore-staged-companions` — 21,881 с. Между началом и
принятием пробного запуска прошло 77,015 с с 16 измерениями. Отдельная
поздняя попытка `recover-native-continuation` завершила фазу без успеха
через 21,621 с. Причина этого результата в метриках не зафиксирована.
Итог операции подтверждён отдельными native ACK2 и отчётом `applied`.
Эти измерения относятся к конкретному переходу и сохраняют отдельно
обязательное наблюдение Console после установки.

## Восстановление Support Access отдельным шагом

После сетевого перехода исходная попытка установки Support Access завершилась
`support_dependency_install_failed`. В Windows был установлен OpenSSH Client,
а OpenSSH Server отсутствовал. Защищённый журнал обслуживания ОС имел состояние
`failed`, CBS не ожидал перезагрузки. Исходный отчёт и журнал сохранены.

Из [официального образа Windows 11 Languages and Optional Features](https://learn.microsoft.com/en-us/azure/virtual-desktop/windows-11-language-packs)
извлечён CAB `amd64` для `10.0.26100.1` с шестью действительными каталогами
Microsoft Windows и SHA-256 `fc40c1573a6dacd58c57e2d85fb6fe9b75a7883b054cc541aa9929453cf7c5cc`.
`Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0 -Source <путь> -LimitAccess`
из локального источника занял 8,395 с, без перезагрузки. Базовый `sshd`
оставался остановлен, новое стандартное входящее правило для TCP 22 отключено.
Процедура соответствует [инструкции Microsoft по автономной установке OpenSSH](https://learn.microsoft.com/en-us/troubleshoot/windows-server/system-management-components/cant-install-openssh-features).

Штатный `--install` подписанного `EndpointSupportAccess.exe` завершился кодом
`0` за 18,215 с. Служба перешла в `Running / Auto / LocalSystem`, Gateway
получил `installed=true` для Support 1.1.9 без ошибки. Повторное наблюдение
за 215,907 с подтвердило стабильный процесс Support, исходный сеанс, свежий
UserSensor и Observer 1.0.13. На той же загрузке Windows остались тот же хэш
четырёх приватных файлов, принятый native ACK2 и две записи установки.
Доступ по политике не включался, SSH-сеанс в рамках этого опыта не проверялся.

В 19:54:49 UTC Console приняла то же назначение и создала лабораторную
квалификацию `6bf526f8-6f1d-40a0-a121-7d200ea6aafc` для исходной Foundation
3.2.205 и точного EXE 3.2.276. Она действует до 25 декабря 2026, 19:54:49 UTC.
Контроль БД подтвердил один лабораторный canary, ноль строк fleet policy и
ноль кампаний с целевой версией. Нативный сетевой результат получен на
`EnterpriseSEval` `26100.1742`. Для `EnterpriseSEval` `26100.9457` и
`EnterpriseS` `26100.9457` отдельные результаты сетевого перехода открыты.
