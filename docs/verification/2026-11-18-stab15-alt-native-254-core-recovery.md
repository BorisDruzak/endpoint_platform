# STAB-15. Восстановление Core при ожидании Support на ALT 3.2.254

После офлайн-переустановки Setup может запустить Core на прежней карточке, когда Gateway принял события удаления и установки, а регистрация Support вернула HTTP 409. Внешний код 21 сохраняется до готовности Support. Штатный `reconcile` после разрешения регистрации завершает ту же операцию с кодом 0. [Согласованная спецификация](../superpowers/specs/2026-11-18-alt-core-recovery-with-support-pending-design.md)

## Исходники и упаковка

Релизный коммит `448c51698b3fe2af5449fcf7a20eead8122be953`. В Linux на чистом архиве этого коммита прошли 184 теста. Проверка списка установочных путей требует собранного Core RPM и при прогоне исходников была пропущена. SHA-256 квитанции `source-254-final.log` — `3f124829355f2ace25e5280dde51a68b47ec46af07e2385023b9f085232bec34`.

На первой сборке проверка извлечённого UserSensor обнаружила, что systemd мог запустить службу политики браузера при перезагрузке до полной готовности. После исправления в собранном RPM служба требует `runtime-ready`. То же условие применяется к службе обновления, её path и службе повторного взвода. Core дополнительно принимает `core-ready`, сохраняя обязательные проверки launcher и selector. Метка `support-pending` запрещает запуск службы Support.

В финальном неподписанном Core проверены 175 файлов, в UserSensor — 18. Оба пакета содержат общую ссылку на манифест Core с SHA-256 `026f3c8981d16e8ae26a2d38725cd0cb09ff7717aa787fbab025064ef43a6d80`. Хеши до подписи и условия извлечённых unit-файлов сохранены в `C:/endpoint-platform-wix-build/stab05-alt-native-254-20261118/final-candidate/checked-unsigned.json` и `unsigned-units.json`.

## Приёмка на ALT Workstation K 11.4 x86_64

На чистом клоне VM208 с systemd 257.9 штатное ручное одобрение создало одну лабораторную карточку. После начальной установки Setup вернул 0, Gateway подтвердил первое событие и принял WSS. При отключённой сети удаление и переустановка той же подписанной пары вернули 21 при нативном коде RPM 0 в обоих случаях. Локально сохранились идентичность, поколение, credential, origin и CA.

| Состояние | Gateway и Setup | Фактическое состояние после холодной загрузки |
| --- | --- | --- |
| Ожидание Support | Gateway подтвердил удаление 2 и установку 3. Регистрация Support вернула HTTP 409, `reconcile` вернул 21. | Core запущен и открыл новую WSS. Support, политика браузера и update path неактивны, systemd зарегистрировал невыполненные условия. |
| Разрешение для той же карточки | Один операторский reset вернул 204. Штатный `reconcile` вернул 0, ACK остался равен 3. | Core, Support и политика браузера запущены, update path ожидает изменений. Политика Support выключена, туннель закрыт. |

На стадии ожидания Core выполнил одну команду `health_v1` в новой сессии. PostgreSQL записал успешный результат в 12:40:11.430981 UTC и действие администратора в 12:40:22.063851 UTC. Монотонное время журнала Gateway на одной загрузке независимо подтверждает, что чтение завершённого результата предшествовало reset на 9,68 с. Агент указал собственное время завершения 12:40:25.254121 UTC. Для сопоставления использовались часы сервера.

При повторной офлайн-переустановке на той же карточке Gateway принял события 4 и 5. Два последовательных вызова `reconcile` получили HTTP 409 и вернули 21. Идентификатор текущей операции, оба файла частичной готовности, четыре файла идентичности и конфигурации, ACK 5 и общее число пяти событий совпали в обеих проверках. В аудите осталось одно исходное подтверждение администратора.

## Обновление с 3.2.251, автономный ремонт и откат

На отдельном клоне VM209 установка подписанной начальной пары 3.2.251 прошла на одной лабораторной карточке с ACK 1. При первом запуске клона обнаружился унаследованный ограниченный сетевой адаптер QEMU. Клон выключили, удалили параметр адаптера и повторно проверили сеть до первой операции Endpoint. Для испытания использовались выделенные Gateway и БД.

| Операция | Код | Приёмка |
| --- | --- | --- |
| Обновление 3.2.251 → 3.2.254 | 0 | ACK 2, точная пара RPM, чистая проверка файлов и новая WSS 3.2.254. |
| Ремонт установленной 3.2.254 без сети | 0 | Setup восстановил изменённый файл документации, входящий в RPM. Проверка файлов прошла, селектор, состояния служб и ACK 2 сохранились. |
| Перезагрузка после ремонта | — | Core открыл новую WSS 3.2.254. На этой сессии выполнен один `health_v1`. |
| Откат подписанной пары с 3.2.254 на 3.2.251 | 0 | ACK 3, точные RPM 3.2.251 и новая WSS на прежней карточке. |

На пяти этапах совпали карточка, поколение и четыре защищённых файла, включая содержимое, inode, владельцев, режимы и ACL. Сводка из 20 квитанций находится в `C:/endpoint-platform-wix-build/stab15-alt254-native-209/summary.json`. SHA-256 сводки — `2c1caf034270da63935e51c7075eb0e527af2ead87d54ffac7ff63ea75503c59`.

После сверки удалены VM209, её диск, выделенные службы и БД. Исходная VM132 осталась выключенной. SHA-256 описи квитанций — `cb60e4ad74be2563cecaca606b981e9b7da8264bade6f605c5e6dcf0a1717974`.

## Первый вход пользователя в Plasma X11

Временный клон VM210 впервые загрузился без сетевого интерфейса, пакетов Endpoint и пользовательской сессии. После чистой установки проверенной пары и регистрации на выделенном Gateway устройство получило ACK 1 и WSS. До первого входа пользователя образца UserSensor на карточке не было.

Файлы настройки LightDM и PAM прошли повторную сверку, оба RPM прошли `rpm -V`, OTA-назначений не было.
