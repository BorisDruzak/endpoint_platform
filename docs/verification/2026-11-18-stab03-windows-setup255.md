# STAB-03. Подтверждение завершения Core в Windows 3.2.255

В 3.2.253 на тестовом дереве Windows вернула управление координатору принудительной остановки, пока оба дескриптора процессов ещё показывали `WAIT_TIMEOUT`. 3.2.255 проверяет завершение каждого учтённого процесса Job перед разрешением смены селектора. [Исходное наблюдение](2026-11-18-stab02-windows-setup253-power-ack.md)

## Поведение при обновлении

Когда завершение прежнего владельца подтвердить не удалось, updater сохраняет точные байты селектора и исходную операцию обновления. Результат `core_stop_unverified` означает, что повторная проверка ещё нужна. Состояние SCM `STOPPED` само по себе не разрешает смену версии.

После обычной перезагрузки, инициированной оператором, updater может проверить ту же операцию снова. Для этого нужны новый идентификатор загрузки ядра и запись 27 Kernel-Boot с типом загрузки 0, более новая, чем сохранённая отметка журнала System. При недоступности этих данных операция остаётся в ожидании. Сам агент перезагрузку не запрашивает.

## Возврат к версии, установленной через MSI

Уже существующий каталог 3.2.255 принадлежит MSI. Если оператор назначает обратное Core OTA с 3.2.256 на 3.2.255, updater требует квитанцию владения ZIP для повторного использования каталога. Без неё он завершает проверку с ошибкой `target version collision with different bytes` до остановки службы и изменения селектора, в том числе при совпадающем содержимом файлов.

При таймауте подтверждения запуска updater может вернуть предыдущий сохранённый селектор после проверки остановки кандидата. Повторная публикация каталога при этом не требуется. Обе ветви проверены четырьмя тестами на коде updater из точного MSI во временных каталогах с имитацией SCM. SHA-256 updater `4154467941875610662b959538ecb82f5c67475b60ed54c3d1e6ee7a28afc531`. Квитанция `C:/endpoint-platform-wix-build/stab03-setup255-reverse-core/proof.json`, SHA-256 `6b009ee3a653370036ab4a46e2aa0c82e3ad505c9f4ad3c511bbb59180512ca2`.

## Установка через штатный Observer на Windows 10

На VM215 и отдельном Gateway VM216 зарегистрировали подписанный Setup и назначили его единственной лабораторной карточке с работающей 3.2.253. В 14:30:02 UTC назначение `fe05cfaf-d445-45d5-8fd9-12613097c207` завершилось как `applied / setup_post_restart_confirmed`. Нативный Setup вернул 0, установленный MSI совпал с артефактом, а Gateway принял установку с ACK 4 и новую WSS 3.2.255 на прежней карточке. Шесть наблюдений охватили 181,207 с связи. На ПК совпали четыре защищённых файла. В этой серии проверяли службы и подключение. Пользовательской сессии с активным UserSensor в шести наблюдениях не было.

Серверная квитанция `native-lab/setup255-provider-terminal.json`, SHA-256 `2d5618ac8b345190bd974da6db3ef471ce88dfa2350fcc71881f9d4577d903d8`. Квитанция гостевой ОС `native-lab/guest255-local-accepted.json`, SHA-256 `a70b9e2e8e33babd42182afe0607650cece612b27549dfe0c9e09b6239783698`. Обе находятся в каталоге сборки 3.2.255.

## Первая попытка Core OTA с 3.2.255

Gateway предложил 3.2.256 той же карточке. По операции `badf4703-7e7c-48dc-bd2e-24c01d2b5e42` лабораторный API зарегистрировал шесть циклов выдачи рекомендации (HTTP 200) и подтверждения запроса (HTTP 204). За этот интервал запросов самого архива было ноль. На госте оставалось 18,6 ГБ, каталог загрузок и файл блокировки ещё не появились. Селектор сохранил 3.2.255, файла pending и перехода на 3.2.256 не было. SHA-256 сводки `stab03-setup255-preget-acl/receipt.json` — `9cfd3ac9856ec384f836a61e126064e59f7ee890ca2d6419b4dd40ab933636d4`.

В 14:36:24 UTC процесс Windows `wlms.exe` инициировал выключение ВМ по истечении срока Evaluation. Это зафиксировало событие User32 1074, запись 434. После следующей загрузки сохранился селектор 3.2.255. Проверка повтора удержанной операции требует, чтобы pending существовал **до** обычной перезагрузки. В этой попытке до такого состояния не дошло. SHA-256 квитанции `native-lab/guest215-shutdown-boundary.json` — `16d9163c02b8ccf05529bfad34f8aaea9271a5d5c90bc5a6e7b559f3e39856f1`.

При следующей штатной попытке Windows Performance Recorder в 14:52:58 UTC зафиксировал у действующего процесса Core два отказа `0xC0000022` в доступе к каталогу `updates`. Перед этим Gateway принял очередное подтверждение запроса. В коде 3.2.255 после этого ACK служба вызывает установку DACL существующего каталога до открытия файла блокировки и до первого GET архива. Каталог принадлежит SYSTEM. Права обоих сервисных SID позволяют изменять файлы, а право записи DACL у них отсутствует. Родительский машинный каталог на этом MSI также защищён и имеет четыре явные разрешающие ACE. Квитанция трассы `native-lab/core256-fileio-retry-receipt.json`, SHA-256 `423c8a3bc03b7b033020292ae0412e446564f82845f08c606d252391be010103`.

## Обычная перезагрузка Windows при ожидающем запросе

В 14:54:14 UTC оператор инициировал штатный Restart тестовой ВМ. До него и после него сохранились селектор 3.2.255 и исходная операция со статусом `requested`. Файла pending ещё не было. Установленный Core открыл новую WSS на прежней карточке. Результат этого Restart позволил отдельно проверить сам способ распознавания загрузки.

| Свидетельство загрузки | До Restart | После Restart |
| --- | ---: | ---: |
| Номер записи System Kernel-General/12 с BootMode 0 | 445 | 500 |
| Номер записи Kernel-Boot/20 и значение LastBootId | 447 / 5 | 502 / 6 |
| Номер записи Kernel-Boot/27 с BootType 0 | 449 | 504 |
| GUID, полученный непосредственно у ядра | `5bd0075d-e39b-11f1-bd82-a47d04902899` | тот же |

Новая запись 504 больше сохранённой отметки 482. Поскольку GUID сохранился, реализация 3.2.255 оставила прежнюю неопределённость. На этом Windows 10 обычный Restart недостаточен для снятия блокировки в 3.2.255. После загрузки системный счётчик BootId имел тип DWORD и значение 7. SHA-256 исходных квитанций `guest-native-boot-before-ordinary.json` и `guest-native-boot-after-ordinary.json` соответственно `fa3befb756c190d990a68d6acb894a9c4e6f1d30c35053c4c45b4fa065eecfa6` и `cccccf00f87994bd9a1f08442d9cf52806278fc534e918af36daab2a2558a659`.

При отдельном штатном Restart в 15:03 UTC счётчик BootId прочитан в обеих загрузках. Он вырос с 7 до 8, поле LastBootId в событии 20 — с 6 до 7. Три новые записи 561, 563 и 565 следовали за прежней отметкой 548. До перезагрузки и после неё SHA-256 XML записи 548 совпал и составил `9e26406992d411850b95c83aa66c68f01d6b8a6738c4eab805cbabb68baeb154`. GUID опять сохранился. Эти два снимка дают проверяемую основу для исправления в следующем кандидате. В установленной 3.2.255 способ распознавания перезагрузки остался прежним.
