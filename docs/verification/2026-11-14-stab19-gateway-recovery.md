# STAB-19 — Репетиция восстановления Gateway и worker

14 ноября 2026 года. Изолированный стенд Windows 11, PostgreSQL 16.15,
Python 3.14.3 и один Uvicorn. Испытан серверный код
`643f13bf075c61c2b8584d16eac99bd4918a888b` со схемой
`0052_inventory_installation`. Для испытаний создана временная база
и синтетические устройства с уникальными учётными данными.

| Сценарий | Свидетельство | Время |
| --- | --- | ---: |
| Остановка API после разрешения старта | Остановлен Uvicorn с открытой сессией, запущен новый экземпляр приложения. Клиент с прежним ID экземпляра отправил сохранённый результат дважды и получил два точных ACK. В PostgreSQL один результат, один снимок health и одна открытая сессия. | 0,610 с от начала остановки до второго ACK |
| Потеря соединений PostgreSQL | Для временной базы запрещены новые подключения и завершены существующие backend-сессии. Сокет закрылся во время отправки результата. После возврата доступа тот же API принял повтор команды с тем же результатом. Worker отразил ошибку и продолжил планирование без рестарта. | 0,107 с до второго ACK, 0,344 с до записанного расписания от возврата доступа |
| Остановка и повторный запуск worker | Два цикла запуска и остановки. Каждый запуск обработал новое устройство, а для уже обработанного устройства повторные активные запросы не возникли. | 0,808–0,867 с суммарно за два цикла |

Таймер worker на этом стенде равен 250 мс. Измеренные интервалы относятся к
синтетическому клиенту, который переподключается сразу после возврата доступа.
Для production остаётся проверить обычный интервал worker, клиентский backoff
и восстановление на Linux с TLS. Восстановление из внешней резервной копии
и фактические RPO/RTO остаются отдельной приёмкой.

```powershell
$env:ENDPOINT_TEST_POSTGRES_URL = 'postgresql://postgres@127.0.0.1:55439/postgres'
$env:ENDPOINT_STABILITY_RECOVERY = '1'
python -m pytest tests/gateway/test_stability_recovery.py -s -q --disable-warnings
```

Выделенный PostgreSQL должен слушать на loopback. Тест создаёт и удаляет
свою базу. Имя временной базы проверяется перед отключением соединений.

## Принудительное завершение процессов

В отдельной репетиции для каждого сценария создан собственный экземпляр
PostgreSQL 16.15 с Alembic head. Uvicorn работал отдельным процессом. Тест
принудительно завершал только запущенный им API либо останавливал собственный
PostgreSQL через `pg_ctl stop -m immediate`. PostgreSQL прошёл автоматическое
восстановление после нечистого завершения, а API продолжил работать с тем же
PID. В сценариях завершения API новый процесс слушал прежний порт.

| Сценарий | Точка сбоя | От начала сбоя до проверки результата |
| --- | --- | ---: |
| API, результат ещё у клиента | Получено разрешение старта, подготовленный результат ещё не отправлен. | 2,477 с |
| API, результат уже записан | PostgreSQL подтвердил наличие записи. Клиент ещё не прочитал ACK. | 2,404 с |
| PostgreSQL | БД остановлена в режиме immediate после разрешения старта. Отправка результата при остановленной БД разорвала сокет. | 2,816 с |

Во всех трёх случаях клиент восстановил связь под тем же ID экземпляра и
дважды отправил сохранённый результат. Gateway вернул точные ACK. В базе
подтверждены один результат, один снимок и одна открытая сессия.

```powershell
$env:ENDPOINT_STABILITY_PG_SERVER_BIN = '<каталог initdb и pg_ctl>'
python -m pytest tests/gateway/test_stability_process_crash.py -s -q --disable-warnings
```

## Восстановление серверного архива на Ubuntu через WSS

16 ноября на изолированном Ubuntu 24.04.3 испытаны процессы из архива
`endpoint-platform-fcad03de9ce5.tar.gz`, исходный коммит
`fcad03de9ce5aee4eefe056793c39ffb8a558a5b`. Использованы Python 3.12.3,
PostgreSQL 16.15, Nginx 1.24 и миграция до `0054_periodic_context_profiles`.
Nginx и PostgreSQL слушали только loopback. WSS использовал отдельный CA
с проверкой имени `localhost`. Контрольный запрос без этого CA отклонён.

Клиент использовал штатные `RuntimeLifecycle`, `WebSocketGatewayTransport`
и SQLite с синтетическим сбором `health_v1`. Прокси TLS оставался запущен
во всех трёх сценариях. В первом API завершён до отправки результата из
исходящей очереди. Во втором API завершён после фиксации результата,
когда испытательный слой удерживал полученный ACK перед обработкой
клиентом. В третьем отдельный PostgreSQL остановлен через
`pg_ctl stop -m immediate` и прошёл автоматическое восстановление.
PID API в этом сценарии сохранился.

| Отказ | Готовность серверного компонента, с | Свежий WSS, с | Очередь SQLite пуста, с |
| --- | ---: | ---: | ---: |
| API до записи результата | 2,068 | 5,093 | 5,196 |
| API после записи, до применения ACK | 2,130 | 5,091 | 5,151 |
| PostgreSQL | 0,234 | 5,147 | 5,221 |

Время отсчитано от начала отказа. Во всех сценариях измерена штатная
пятисекундная задержка клиента. Две попытки отправки использовали
одинаковый результат из SQLite. На каждый сценарий пришлись один вызов
обработчика, один результат и один снимок в PostgreSQL, одна открытая
WSS-сессия после восстановления.

Отдельно проверен архивный worker без изменения интервала планирования
60 секунд. Первый запрос поставлен за 61,937 с от запуска worker.
После принудительной остановки и запуска нового процесса запрос для
второго устройства поставлен за 62,119 с. Для первого устройства
сохранилось одно назначение.

Прошли три WSS-теста и один отдельный тест worker. На первом прогоне
WSS остановился при импорте `wsproto`, отсутствовавшего в тестовых
зависимостях. Повтор использовал также `requirements-server.txt` из
архива. Единственное различие между списками установленных зависимостей
было добавление `wsproto==1.3.2`. Тестовые процессы и каталоги удалены.
Испытание измеряет восстановление одной синтетической команды при каждом
отказе. Приёмка под совместной нагрузкой Endpoint и Helpdesk остаётся
отдельным этапом.

## Восстановление после остановки диспетчера доставки

В локальном тесте до исправления и исключение, и неожиданный
возврат задачи диспетчера оставляли API запущенным. Новая задача
доставки не появлялась за 3 с в обоих сценариях.

В `4168564077006bf0d3831516afbcd431a748308f` supervisor пишет безопасный
код завершения, закрывает текущие WSS-сессии и через секунду
повторно запускает диспетчер. Повторное подключение проходит
штатную проверку владельца доставки. Сообщение исключения
со значением из тестовой фикстуры в журнал не попало.

Обе проверки зафиксировали доставку в SQLite и прервали работу
до выдачи кадра. После перезапуска диспетчера и открытия новой
сессии повторилась исходная команда, а та же строка доставки
получила ID новой сессии. Штатная остановка приложения завершила
супервизор. Прошли 472 теста Gateway, Context и Architecture
с 26 пропусками.

Для того же исходника Windows release gate дал 2 915 проходов
и четыре пропуска, Console выполнила 125 тестов. Два серверных
архива совпали побайтово. Состав архива сверили по 332 исходным
и трём собранным файлам. Квитанция `candidate-artifacts.json`
сохранена в `C:/endpoint-platform-wix-build/stab19-gateway-dispatch-recovery-20261117/server-release`.
SHA-256 — `45f972dbec8de1366c5a736b90d446fb149779ef295b9b7d341df63a5b1a154f`.

## Смена владельца WSS во время ожидания отправки

В тесте Gateway сохранил доставку в SQLite и ожидал блокировку
отправки. До исправления прежний сокет получил команду после
регистрации новой сессии. В `41e3fd4bd38085116cad2f0297cb525b6c0eddba`
Gateway проверяет владельца внутри блокировки непосредственно перед
началом отправки. Прежний сокет получил ноль кадров. Через новую
сессию передалась та же команда с исходной строкой доставки. Тест
проверяет момент до начала отправки кадра.
