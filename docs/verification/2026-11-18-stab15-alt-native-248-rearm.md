# ALT 3.2.248 — восстановление watcher после start-limit

На подписанном 3.2.246 при серии локальных событий OTA systemd
вернул `start-limit-hit` для updater и `unit-start-limit-hit` для
watcher. Запрос отката остался на диске. В изолированном тесте на
systemd 257.9-alt1 запрос оставался необработанным после истечения
масштабированного лимита 12 секунд при burst 3. Руководство systemd
подтверждает переход watcher в failed при исчерпании лимита updater.
[systemd.path 257](https://www.freedesktop.org/software/systemd/man/257/systemd.path.html)

Исправление `25f8d885351ac430a9b29525fb52ff1cffb3a751` применяет
отложенный RPM rearm. После отказа path запускается одноразовый timer
на 16 минут. Он запускает rearm только когда path включён и находится
в failed. Остановка watcher останавливает rearm. Для native RPM rearm
также требует `runtime-ready`. Ограничение updater сохраняет 900 секунд
и burst 3. Таймер не сбрасывает счётчик и не опрашивает службу.
[systemd.timer 257](https://www.freedesktop.org/software/systemd/man/257/systemd.timer.html)

В изолированных units на ALT systemd 257.9 с коротким таймингом
подтверждены автоматическая обработка сохранённой заявки, обработка
новой заявки после восстановления, остановленный и выключенный watcher,
отсутствие `runtime-ready` и сохранение заявки при
постоянной ошибке с максимумом три старта в одном окне.
Отдельный штатный harness исходного helper проверил сохранение PID Core
при отказе до остановки, kill/timeout до и после переключения, ручную
остановку Core, административное отключение во время обновления и
устаревшее владение от предыдущей загрузки.

Для выпуска подготовлен отдельный исходник
`7bd7086a4650c9c9abd2218b2b9bbd0633235302`, версия 3.2.248.
Тесты исправления прошли 70 с 4 пропусками. Тесты подготовки кандидата
прошли 56 с 7 пропусками. `bash -n packaging/alt/build-rpm.sh` и
`git diff --check` прошли. Подписанные 3.2.246 сохранены в исходном виде.
Изолированный полный оборот 3.2.246 описан в
[отчёте ALT 3.2.246](2026-11-18-stab15-alt-native-246.md).

## Установленный rearm и Gateway, VM186

Чистый клон ALT Workstation K 11.4 использовал изолированный мост без
маршрута по умолчанию, отдельный Gateway/worker и отдельную PostgreSQL
15 со схемой `0056_context_collection_history`. Штатный verifier
опубликовал 3.2.248 только в этой БД с ID
`75523694-876c-4ed9-8890-64db63212b97`. Единственное ручное разрешение
`59ca4559-2869-451a-81d0-963d0d6553f0` ограничено точной парой RPM и
адресом VM186 на закрытом мосту. TLS проверялся штатным именем и
существующим лабораторным CA.

На VM186 Setup установил точную пару с native 0, на первом вызове
вернул 21 до ручного подтверждения. После HTTP 204 штатный
`reconcile` вернул 0. На свежей карточке
`508ae30d-2dcc-4ff5-927a-46799b191958` сохранено ровно одно событие
`b9163f88-e0a5-4131-9cea-cadc88ecd0c7`, sequence 1/ACK 1 и
`bootstrap=complete`. Gateway принял 3.2.248 в WSS
`9137c313-632b-4313-826d-4ada569f5ff2`. В активном локальном X11-сеансе
LightDM штатный XDG autostart запустил UserSensor из 3.2.248 и
`endpoint-kde-probe`. Политика назначена только тестовой карточке.
Gateway принял `READY` и отметку UserSensor
`2026-11-17T21:23:05.045936Z`.

Только для сценария VM186 тайминг изменили временными настройками
`/run/systemd/system` до 12 секунд для окна updater и 13 секунд для
rearm. Лимит три запуска, условия запуска и упакованные units сохранились.
Три корректно сформированных запроса на архив без установленной
подписи завершились отказом до остановки Core. Четвёртый запрос на тот
же архив, уже с авторизацией штатного издателя, сохранился в pending
при `unit-start-limit-hit`. Установленный rearm восстановил watcher,
обработал исходный запрос `d5c00e11-4825-4d10-9b3e-ecefffd55b94` и
записал один успешный результат. Gateway принял 3.2.206 в WSS

`33581730-1d58-495b-aee4-13867d28c69e` той же карточки.
