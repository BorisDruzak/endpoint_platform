# STAB-19 — Локальный замер пропускной способности Gateway

14 ноября 2026 года. Код сервера `1bdee6ec1522a667ae84e0a62c18a75f52249e5c`,
схема `0052_inventory_installation`. Один Uvicorn 0.34.0, PostgreSQL 16.15,
Python 3.14.3, SQLAlchemy 2.0.51, asyncpg 0.31.0, aiohttp 3.13.3.
Стенд Windows 11 build 26100 на i5-10400, 6 ядер, 12 потоков, около 32 ГиБ ОЗУ.
Gateway, PostgreSQL и генератор нагрузки работали на одной машине.

## Протокол

Для каждого размера открывается одна TCP/WebSocket-сессия на синтетическое
устройство. Затем все устройства одновременно заменяют соединения под теми
же идентификаторами экземпляров, пока старые соединения ещё открыты. На
каждом подключении Gateway выдаёт одну заранее поставленную команду
`context.health.collect`, принимает heartbeat, разрешает старт после ACK,
записывает результат и выдаёт `result_ack`. После волны проверяются число
открытых записей сессий, число владельцев в registry, число сохранённых
снимков и отсутствие незавершённых коллекций для этой группы.

Прогон использует loopback и доверенные заголовки прокси. Для проверки
готовности к расширению на production остаётся повтор на Linux с реальным
TLS-прокси, работающим worker, включёнными политиками, фоновой нагрузкой,
длительным удержанием соединений и штатным распределением heartbeat.
Измеряется один завершённый результат на устройство за волну.

```powershell
$env:ENDPOINT_TEST_POSTGRES_URL = 'postgresql://postgres@127.0.0.1:55439/postgres'
$env:ENDPOINT_STABILITY_CAPACITY = '1'
python -m pytest tests/gateway/test_stability_capacity.py -s -q --disable-warnings
```

Тест использует временную базу с миграциями и проверяет loopback-адрес
PostgreSQL. Номер порта в примере относится к выделенному кластеру стенда.

## Кандидаты на SLO для следующей репетиции

| Метрика | Предлагаемый критерий |
| --- | --- |
| Задержка цикла событий | p99 ≤ 50 мс в штатной работе и в волне переподключения |
| Разрешение старта и ACK сохранённого результата | p95 ≤ 1 с для каждого при штатной нагрузке |
| Время от постановки до доставки команды подключённому устройству | p95 ≤ 5 с при штатной нагрузке |
| Переподключение после возврата API или PostgreSQL | ≥ 95% ожидаемых устройств восстанавливают работу за 60 с, с учётом клиентского backoff |
| Очередь после всплеска | Очередь возвращается к исходному размеру за 60 с, без повторного применения подтверждённых результатов |

Целевые значения предстоит проверить на представительном стенде. Для
интерпретации задержки доставки нужна отметка момента постановки запроса.
Задержка открытия сокета и доставки в тесте сообщается от начала клиентского
подключения, длительность волны включает все команды и запись результатов.

## Прогон на Linux через TLS

32 синтетических устройства, 125,070 с сессий и 64 записанных результата
`health_v1`. Первый набор из 32 запросов создал штатный worker с интервалом
60 с. Второй набор подготовлен перед одновременной заменой всех соединений.
После замены осталось 32 открытые сессии и 32 владельца в registry.

Стенд Ubuntu 24.04, четыре vCPU, 16 ГиБ ОЗУ. API, worker и клиенты в одном
процессе Python внутри контейнера с лимитом 2 ГиБ. Nginx 1.30.5 и
PostgreSQL 16.15 находились в отдельных контейнерах. Соединения шли через
Nginx с проверкой тестового CA и имени `localhost`. Uvicorn 0.54.0,
wsproto, Python 3.13.16, SQLAlchemy 2.1.8 и aiohttp 3.14.5. Исходный код
сервера `eaa04f579a549b55e9aa18e02a3bcf1b92c6d7d2`, схема
`0052_inventory_installation`. Флаг Endpoint Policy включён, активных
назначений политик у синтетических устройств нет.

| Метрика | Первое подключение | Замена сессий |
| --- | ---: | ---: |
| Hello p95 | 770,9 мс | 731,0 мс |
| Разрешение старта p95 | 386,0 мс | 316,2 мс |
| ACK результата p95 | 762,7 мс | 773,4 мс |
| Доставка p95 от начала переподключения | — | 965,4 мс |

Event loop p99 составил 6,9 мс, максимум — 207,9 мс. Первый набор команд
читался приложением теста после отметки 90 секунд. Поэтому отображённое
тестом время этой фазы включает ожидание стенда. Измерения охватывают
очередь `health_v1`. Остальные типы Context, которые worker поставил в
очередь, остаются вне нагрузки, заданной этому профилю клиента.

Для повтора настройте Nginx на `127.0.0.1:18443` с сертификатом на
`localhost` и upstream `127.0.0.1:18081`. Передавайте Upgrade/Connection,
`X-Forwarded-Proto=https` и `X-Forwarded-For` из адреса клиента.
Укажите доверенный тестовый CA в `ENDPOINT_STABILITY_TLS_CA` и адрес
отдельной loopback PostgreSQL в `ENDPOINT_TEST_POSTGRES_URL`. Запуск:
`python -m pytest tests/gateway/test_stability_tls.py -qs`.

Следующая ступень для оценки ёмкости production — более длительный прогон
на версии Python и зависимостях из production, с раздельными процессами
API/worker, нагрузкой соседних сервисов и профилями реальных агентов.

15.20 с отдельной БД для каждого прогона работал на той же VM.
Зависимости стенда — Uvicorn 0.54.0, wsproto 1.3.2, SQLAlchemy 2.1.8,
