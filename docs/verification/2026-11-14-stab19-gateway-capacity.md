# STAB-19 — Локальный замер пропускной способности Gateway

14 ноября 2026 года. Код сервера `1bdee6ec1522a667ae84e0a62c18a75f52249e5c`,
схема `0052_inventory_installation`. Один Uvicorn 0.34.0, PostgreSQL 16.15,
Python 3.14.3, SQLAlchemy 2.0.51, asyncpg 0.31.0, aiohttp 3.13.3.
Стенд Windows 11 build 26100 на i5-10400, 6 ядер, 12 потоков, около 32 ГиБ ОЗУ.
Gateway, PostgreSQL и генератор нагрузки работали на одной машине.

## Протокол

Для каждого размера открывается одна TCP/WebSocket-сессия на синтетическое
устройство. Затем все устройства одновременно заменяют соединения под теми
же идентификаторами экземпляров, пока старые соединения ещё открыты. На
каждом подключении Gateway выдаёт одну заранее поставленную команду
`context.health.collect`, принимает heartbeat, разрешает старт после ACK,
записывает результат и выдаёт `result_ack`. После волны проверяются число
открытых записей сессий, число владельцев в registry, число сохранённых
снимков и отсутствие незавершённых коллекций для этой группы.

Прогон использует loopback и доверенные заголовки прокси. Для проверки
готовности к расширению на production остаётся повтор на Linux с реальным
TLS-прокси, работающим worker, включёнными политиками, фоновой нагрузкой,
длительным удержанием соединений и штатным распределением heartbeat.
Измеряется один завершённый результат на устройство за волну.

```powershell
$env:ENDPOINT_TEST_POSTGRES_URL = 'postgresql://postgres@127.0.0.1:55439/postgres'
$env:ENDPOINT_STABILITY_CAPACITY = '1'
python -m pytest tests/gateway/test_stability_capacity.py -s -q --disable-warnings
```

Тест использует временную базу с миграциями и проверяет loopback-адрес
PostgreSQL. Номер порта в примере относится к выделенному кластеру стенда.

## Тайминги SQL и повторное чтение владельца доставки

16 ноября 2026 UTC на прежней VM142 выполнены три прогона по 96 устройств
через Nginx/TLS с отдельными процессами Gateway, worker и клиента.
Первые два использовали неизменённый сервер
dc176a75dbbb4dfd47cb33424f5b03e8f474a3a0 и лимиты 15 и 30. Третий
использовал лимит 15 и `command_service.py` с исправлением
1c559f33ee0dd167ba474a3d948bf1d1eab25fc9. В каждом прогоне удержание
сессий составило не менее 125 с. Подтверждены 192 результата и 96
владельцев сессий, без ошибок получения соединения.

Сценарий измеряет `Pool.connect()`, время от выдачи до возврата
соединения и завершённые операции между `before_cursor_execute`
и `after_cursor_execute`. Последняя метрика учитывает время драйвера
и планирования. Метрики агрегированы отдельно, SQL и параметры в
отчёт не пишутся. Время удержания охватывает обработку на выданном
соединении. Суммировать отдельные P95 для одного ACK нельзя.

| Вариант | P95 получения, мс | P95 удержания, мс | P95 выполнения SQL, мс | SELECT за волну замены | P95 ACK результата, мс |
| --- | ---: | ---: | ---: | ---: | ---: |
| Лимит 15, исходный код | 991,1 | 177,1 | 12,5 | 4987 | 2293,9 |
| Лимит 30, исходный код | 1034,0 | 343,3 | 27,0 | 4982 | 2142,6 |
| Лимит 15, исправление владельца | 1015,9 | 171,4 | 12,6 | 4890 | 2176,1 |

При лимите 30 P95 выполнения SQL и удержания соединений выросли. Ускорение ACK
относительно лимита 15 в этом повторе не согласуется с предыдущей
парой прогонов. Результаты не дают основания менять боевой лимит.

GitNexus нашёл `record_result` в модуле Gateway. Вызов из обработки
WSS-результата проверен по исходнику. Для результата из текущей сессии
заблокированная запись `DeviceSession` уже подтверждает устройство
и экземпляр. Исправление использует эту запись, когда доставка
принадлежит той же сессии. Для доставки из предыдущей сессии остаётся
проверка её экземпляра. Регрессия на двух ветках подтверждает ноль
повторных чтений владельца в текущей сессии и одно после переподключения
того же экземпляра, оба результата получают корректный ACK.
Существующие проверки отвергают конфликтующие повторы и передачу
результата другому экземпляру.

`SELECT` меньше. Количество `INSERT` и `UPDATE` сохранилось
на 576 и 1248. Регрессионный тест отдельно связывает один пропущенный
запрос с каждым результатом из текущей сессии. Короткое сравнение
до и после не устанавливает устойчивый выигрыш в задержке.
