# STAB-02 — ALT 11.4 3.2.265 после потери питания и штатный repair

19 ноября 2026 года в закрытой сети проверили свежую установку подписанных Core и UserSensor `3.2.265-alt6.x86_64` на одноразовой VM259. Ревизия комплекта `010e1fd5d3ffac17f24b7a4c50bf1dabdc2dce97`, SHA-256 архива `09310c8b93bbcfd410cdd96718647fccc3d55360aa94bf0674955626bb61b216`. У отдельного Gateway и PostgreSQL на VM260 была одна вручную одобренная тестовая карточка. Обе ВМ использовали только `vmbr259` без внешнего маршрута. До отключения питания ВМ штатно не перезагружали.

## Результат записан, ACK ещё удерживается

Выделенный Gateway удерживал только `result_ack` для команды `health_v1` `db6fa40b-7d89-4860-90d6-0528a53967f8`. В БД уже были результат `32efd508-740b-45eb-9f04-2c9b3a0af5ba` и снимок `e4820da5-ea21-426f-b02d-c2711d8a9718`. Локальный SQLite содержал одну ожидающую запись outbox.

После отключения новый boot ID, новая WSS, прежние идентичность и поколение устройства, lifecycle sequence/ACK 1. Оба `rpm -V` вернули 0. Gateway наблюдал один командный кадр и три кадра результата с одним SHA-256 `100354d144994a7be2a14206cb504bc4776a3cdcc8785c07917cf709669a5a44`. В БД остались исходные результат и снимок без дублей. После ACK с wire sequence 1 outbox опустел. Отдельное отключение между стартом команды и записью результата не выполняли.

## Support до и после отключения

До отключения журнал первого boot содержит один Start без `support_service_unavailable`. Gateway принял штатные `register` и `status` с HTTP 200. Последний отчёт показал installed=true, grant выключен, туннель отключён и `last_error_code=NULL`. Это подтверждает штатный старт, регистрацию и один отчёт состояния при выключенном доступе. Устойчивость процесса во времени, открытие туннеля и рабочий SSH-сеанс этим прогоном не проверялись.

На следующем boot первый `support_service_unavailable` появился через 0,55 с после Start, журнал сохранил 112 таких выходов с кодом 1. Цикл повторился после обычной перезагрузки. После отключения все четыре файла ключевых пар Support имели размер 0 байт, владельца root:root, mode 0600 и mtime времени установки. Содержимое не читали, ключи не меняли. Код `PrivateStore.keys` в подписанной ревизии проверяет уже существующие пары при старте и вызывает `ssh-keygen` непосредственно для целевых файлов при генерации, без явного `fsync` этих файлов в данном пути. Пустые файлы объясняют отказ проверки пар. Потеря несброшенных данных при отключении согласуется с фактами, но предаварийной квитанции о размере файлов нет и точный механизм повреждения не установлен. ## Штатный repair

Два запуска вернули 21 в `PREPARING` до запуска RPM. В обоих исходных снимках unit Support уже был `activating/auto-restart`. Квитанции не различают отказ из-за самого состояния и отказ из-за рассогласования при повторном чтении перед остановкой. Штатный `reconcile` вернул 0 для каждой исходной операции, сохранил её ID, выставил `not_started_recovered` с native exit null и сохранил защищённую идентичность.

Отдельный repair `fec437c6-b176-4544-a5b8-6c9f50f95c79` выполнили с явно остановленным Support в VM259 при сохранённом enablement `enabled`. Setup и RPM вернули 0, хеш README совпал с извлечённым из подписанного RPM. Оба `rpm -V` прошли до и после обычной перезагрузки. Сохранились защищённые файлы, устройство, поколение и lifecycle ACK 1. Новая WSS `bceda4a1-409d-46bc-8eea-c5008d22ede3` доставила свежий `health_v1` `d29c5ca0-81d3-459e-a676-f5958baa4368`, завершённый в 10:01:39.755559Z. Repair с активным исправным Support остаётся открытым.
