## Пределы локальной проверки

`storage.db` прочитана в неизменяемом режиме через QGA при остановленном Core. Файл не менялся с 07:39:02.386061 UTC, ещё до открытия WSS. Число строк во входящих командах, ожидающих отправки результатах, кэше завершений и резервированиях запуска равно нулю. Идентификатор результата для сопоставления не найден. [Квитанция SQLite](C:/endpoint-platform-wix-build/stab15-win11-online264-130/read-only-vm130-sqlite-result-correlation-20261120.json)

Штатный launcher .264 задаёт `gateway_wss` и отключает HTTP pull fallback. Локальный журнал команд включается, когда обе стороны объявили `COMMAND_JOURNAL_FEATURE`. Сверенный обработчик Gateway эту функцию не объявляет. В таком режиме Core может отправить результат прямо по WSS, поэтому пустая БД не позволяет идентифицировать отправителя.

Установка .264 и начальное подключение подтверждены. Устойчивость этой staging-сессии после 08:39 UTC не подтверждена. При проверках использовали чтение QGA и журналов staging. Повторной отправки результатов, перезапуска служб и изменений VM не выполняли.

У подписанной .275 и .264 совпадают Git-деревья `pc_agent/runtime` и `pc_agent/transport`. В .275 временная потеря связи запускает повторное подключение внутри работающего Core. При терминальной ошибке транспорта Core может завершиться с кодом 1. Дополнительная запись об этом исходе в Windows Event Log появилась в интеграционном коммите `6c0d1933f9e08477e74e1853573b7632ae84ed92`. Она отсутствует в исходнике подписанного Setup .275. Проверка на исходнике .275 прошла по пяти тестам, а интеграционная ветка прошла десять, включая запись терминального отказа и проверку штатных завершений.
