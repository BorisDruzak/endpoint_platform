# Пилот серверных агентов и каналов доставки

Проверка 11 ноября 2026 года. Windows Core 3.2.193 и отдельный пакет Ubuntu Server 3.2.192 работали с изолированным контроллером Endpoint на `192.168.100.19`. Для каждого хоста были приняты `baseline_v1`, `health_v1`, `inventory_v1`, `network_v1` и `session_v1`. После отключения основного маршрута резервный вход того же контроллера принял новую WSS-сессию и свежий `health_v1` с прежней идентичностью устройства.

| Хост | ОС | Проверенный профиль | Результат |
| --- | --- | --- | --- |
| 192.168.100.10 | Windows Server 2019 x64, 17763 | AD и Directum RX | 8 служб и 5 локальных проверок прошли, C: заполнен на 95,0% |
| 192.168.100.11 | Windows Server 2022 x64, 20348 | AD и КонсультантПлюс | 7 служб и 5 локальных проверок прошли, C: заполнен на 57,3%, S: на 22,2% |
| 192.168.100.19 | Ubuntu Server 24.04 amd64 | Endpoint Platform | 4 службы и локальный HTTP 200, корень заполнен на 98,6% по показанию агента |

На обоих Windows-хостах опрос SCM не обнаружил службы `EndpointAgent` и `EndpointAgentUpdater`. Пилот запускал временный Core на Windows и временный systemd unit на Ubuntu. Приёмка установленной службы и обновления Windows через Console ещё требуется. Локальный OpenVPN-профиль проверен автоматическими тестами, живой приёмки на `192.168.100.30` не было.

На изолированном HTTPS-источнике APT принял подписанный индекс, скачал обе версии и отверг изменённый индекс. В отдельном корне `dpkg` установка 3.2.191, обновление до 3.2.192 и откат сохранили тестовую идентичность и роль. В этом тесте зависимости предоставлялись из подготовленного окружения. Производственный индекс APT и доверенный ключ издателя ещё предстоит настроить.

## Условия для установки

- Production `endpoint.sosnadmin.local` и staging `endpoint-staging.sosnadmin.local` вернули HTTP 200 по HTTPS с CA Endpoint. Их реестры устройств раздельны. Для production нужен второй вход в Gateway с тем же реестром. Пилот проверил обрыв соединения и переключение между входами одного контроллера.
- Windows-канал Full Setup использует системное хранилище сертификатов. На `.11` его HTTPS-клиент принял оба адреса. На `.10` отсутствует CA Endpoint в `LocalMachine/Root`, клиент отклоняет оба сертификата.
- На разделе `/` production доступно около 504 МиБ, staging — около 303 МиБ. Перед развёртыванием контроллера и публикацией пакетов необходимо обеспечить место для новой и предыдущей версий. Оба окружения пока используют ревизию `24461a70286e`.
- Для Ubuntu потребуется выданная production-контроллером пара файлов регистрации, а для Windows — нативный пилот подписанного Setup с подтверждением запуска служб и работы канала обновления. Постоянную установку на целевых серверах не проводили.

## Подготовка production и AD-MAIN

- В production включён [резервный вход Nginx](../../deploy/server/endpoint-platform-reserve.nginx.conf) по адресу `https://endpoint.sosnadmin.local:8443`. Он обслуживает `/healthz` и `/agent/v1/connect`, подключён к тому же API на `127.0.0.1:8000` и доступен с `.11` и самого Endpoint. С `.11` на 443 и 8443 получены HTTP 200 для health и 403 для WSS без авторизации. Оба входа используют один хост и один контроллер. Переключение зарегистрированного агента через этот вход ещё предстоит проверить.
- На `.10` Kaspersky Endpoint Security дважды записал событие 302 с `HEUR:Trojan.Win32.Generic` и точным SHA-256 Setup 193 из таблицы выше. Причина отказа чтения установщика подтверждена журналом файловой защиты. На `.11` Microsoft Defender проверил те же подписанные байты Setup 193 без срабатываний. Это отдельный результат проверки Defender. На `.10` импортирован CA Sosnadmin с отпечатком `EFBED1F8572927112500D8A6E3437CEBB63F9E64`, сверенным с `.11`. Штатный HTTPS-клиент Windows получил 200 от production и staging.
- После сверки с сохранёнными оригиналами удалены только дубли временных файлов Setup/MSI 173 и 174 и их манифесты из двух каталогов `/tmp`. Свободное место выросло с 504 до 1058 МиБ. После регистрации 193 и подготовки контроллера осталось около 737 МиБ.
- Подписанный Setup 193 зарегистрирован для пилота как установщик `1cc15ab5-9a21-49ee-9102-033bb7eff32b` и релиз полного обновления `613ee59a-5a82-43f4-a137-612e965c289e`. Оба связаны с точным SHA-256 выше. Кандидат не включён в общий AUTO. Серверный архив `a901eed124a9` распакован и проверен по 359 записям в отдельной директории релиза. Состав зависимостей, миграции и импорт конфигурации проверены. Переключение production на этот релиз ещё не выполнялось.
- Нативный preflight Setup 190 и 193 на AD-MAIN подтвердил отсутствие исходной Foundation и достаточное место. В Console создана разовая ручная кампания для `192.168.100.11/32` и опубликованного Setup 177. Подписанный Setup 177 прошёл проверку Defender и запустил первичную установку. На 18:18 по Екатеринбургу запрос `b7b9c365-5b78-4006-82c5-6efc5bf0bd72` ожидал одобрения. Успешного завершения нативной установки, назначения 193 и проверки переключения production WSS ещё нет.
