## Windows Setup и наблюдение за компонентами

На момент снимка в таблице Setup было пять `applied` для 3.2.205 и
ноль активных назначений, включая `recovery_required`. В решениях текущей
автополитики четыре `setup_post_restart_confirmed`, одно `already_current`,
десять `waiting_reconnect`, шесть `source_not_qualified`, девять
`platform_unknown`, два `installation_removed` и девятнадцать
`platform_unsupported`. История назначений и решения текущей автополитики
имеют разный охват.

У 11 Windows и 10 Linux устройств была незакрытая непросроченная WSS-сессия
с отметкой за последние пять минут. Отдельные свидетельства для карточки
устройства и обзора парка:

- Core — версия экземпляра и отметка свежей WSS-сессии.
- Foundation — последняя версия, измеренная Setup observer, с датой.
- Updater и observer — собственные версии, свежесть и результат проверки
  готовности каждого компонента, когда такой результат доступен.
- UserSensor — время принятого события реальной пользовательской сессии.
- Support — время и результат фактически выполненного действия, отдельно
  от сведений об установке или доступности.

Для каждого компонента сохраняйте собственную дату наблюдения. Если
свидетельство отсутствует или устарело, показывайте это в карточке.

Вкладка «Обзор» запрашивает эти сведения через `include_components=true`.
Свежий отчёт Support и операторское подтверждение SSH показаны отдельными
строками. Свежесть UserSensor требует также принятой телеметрии активности,
поступившей после наблюдения сенсора или одновременно с ним. Updater получает
отдельное наблюдение в `health_v1`: статус службы Windows SCM либо статус
службы и path unit на ALT. Остановленная служба и активный наблюдатель ALT
могут сосуществовать при ожидании задания. Данные считаются устаревшими
через десять минут от времени сбора на устройстве. Версия updater этим
наблюдением не устанавливается. Агенты без наблюдения показывают «Нет данных»,
а недоступная или отсутствующая служба показывается как неизвестная.

### Расхождение SCM и health на установленном Windows Setup 3.2.226

16 ноября на VM143 с Windows 10 build 19045 и Setup 3.2.226 контроллер
служб показал `EndpointAgentUpdater: Stopped / Manual`. Нативный
Core с PID 2664 сохранил работу. Через лабораторный Gateway в отдельной
копии PostgreSQL принят свежий `health_v1` в 01:47:22 UTC.
Снимок и API карточки показали `EndpointAgentUpdater=unknown`,
хотя SCM показывал остановленную службу. Стенд использовал настоящий
подписанный Setup из предыдущей приёмки. SHA-256 установленного updater
совпал с файлом исходной сборки, оба файла имеют статус
`Authenticode=NotSigned` как отдельные EXE внутри этой сборки.

Временная задача от LocalService получила код 5 при `sc.exe query`,
`sc.exe qc` и ошибку доступа при `Get-Service`. Политика установленной
ревизии даёт виртуальному SID службы `EndpointAgent` право запуска
updater. Для `psutil 7.2.2` вызов `win_service_get` дополнительно читает
конфигурацию службы до обращения к её статусу.

В исходной ветке чтение состояния теперь запрашивает
`SC_MANAGER_CONNECT` и `SERVICE_QUERY_STATUS`. Штатная установка
добавляет `SERVICE_QUERY_STATUS` существующему виртуальному SID
`NT SERVICE\EndpointAgent`. Полный доступ принадлежит SYSTEM и
Administrators. Новое разрешение получает только SID службы.
В проверках Windows, контекста, упаковки MSI и API Console прошли 377
тестов, пять пропущены.
Новая подписанная сборка и повтор штатного запроса проверены ниже.

VM143 штатно выключена и возвращена к конфигурации без сетевого
адаптера. Временные службы и копия БД удалены, исходная лабораторная
БД сохранила отозванный credential. Gateway и worker VM142 работают.

### Нативная приёмка Windows Setup 3.2.237 на VM143

На Windows 10 build 19045 выполнен прямой переход с подписанного Setup
3.2.226 на 3.2.237. EXE и MSI проверены по SHA-256 и Authenticode с
отметкой времени. Исходный коммит сборки
`c9383198278e77cae79cb70bf23eca73812e5301`. Кандидат зарегистрирован
в отдельной копии лабораторной базы с `download_published=false` и
отключённым AUTO enrollment.

Setup завершился за 279,55 с с `0 / SERVICE / UPDATED / SERVICE_RUNNING`.
Новый MSI зарегистрирован, хеш его `LocalPackage` совпал с подписанным
MSI. Совпали четыре локальных файла идентичности, включая origin и CA.
В PostgreSQL одна запись установки на sequence 9 с native 0.
Локальный журнал и серверный ACK содержат один и тот же идентификатор
`fabb6b2f-7617-5c01-9962-ca70fa066455`. Новый WSS 3.2.237 принят на
прежней карточке `3e0c83c6-b0dd-4487-8619-9049456c42c9`.

До и после установки SCM показывал `Stopped / Manual`. Маска
виртуального SID службы `EndpointAgent` в DACL updater изменилась
с `0x10` на `0x14`. Две остальные записи дают полный доступ SYSTEM
и Administrators.

WSS-сессии нового Core. Снимок

отчёта Setup Observer и отсутствие подтверждённого доступа Support
проверены как отдельные поля.
