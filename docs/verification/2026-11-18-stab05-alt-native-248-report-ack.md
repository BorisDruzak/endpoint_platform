# STAB-05. Повтор terminal report на ALT 11.4 после потери ответа

Для проверки использовали штатный архив Core 3.2.206 размером
21 763 666 байт, SHA-256
`ebb77e1a8a2adb9730669e1ef16ccbfe6a781fbc0a2747b6fa0fd209d40ad504`
и сохранённую подпись авторизации. Архив и подписанная пара 3.2.248
сохранены. В закрытой сети работала одна тестовая карточка на прогон.
В проверенном наборе единственный сохранённый подписанный Core OTA
был 3.2.206. Для проверки отчёта 3.2.248 использовали нативный переход
с 3.2.183, который сохранил штатный отчёт об отказе.

## Повторное применение одного назначения в первом прогоне

На Core 3.2.183 сервер сохранил одно назначение. В журнале клиента для
той же операции сначала появился отказ, затем успешное применение
3.2.206. До получения подтверждения агент дважды передал назначение
установщику, и второй запуск изменил уже известный локальный результат.
На сервере в этот момент оставался статус `scheduled`.

В исходниках 3.2.248 обнаружена та же проверка готовности. Исправление
`02a45aced86254c97dd782b37c392289828b1b0e` сверяет идентификатор
назначения с историей установщика и журналом отчётов. Оно выполняет
проверку до скачивания и ещё раз под блокировкой перед передачей
установщику. Новое назначение на ту же версию сохраняет обычный путь
установки. Три регрессионные проверки воспроизвели дефект на старом
коде и прошли после исправления. Исправление вошло в исходники ALT
3.2.249, ревизия `8a82b96ffa29994283b16d5b15afbc255d3cc469`.
На этой ревизии в Linux прошли 103 теста журналов, обновления и сборки.
Два теста гонки между процессами требуют Windows. Для POSIX-проверки
режимов файлов использовали umask 022. При исходном umask 002 тестовые
каталоги получали режим 0775, и тест отката корректно фиксировал отказ.

## Повтор сохранённого отчёта под Core 3.2.248

На свежем клоне операция `1bdb2ea3-70d3-494e-a10e-e6cbdf326c44`
из rollout `7cba6aba-bd26-406f-ad64-b95a4b660c9a` воспроизвела
штатный отказ установки. После появления
одного durable failed report rollout поставили на паузу через
обычный API (HTTP 200). Подтверждение scheduled уже было сохранено.
Пауза убрала новые рекомендации для этого перехода и сохранила
возможность принять terminal report. Штатный Setup обновил подписанные RPM с 3.2.183 до 3.2.248.
Карточка `1f3841a3-03fe-45c2-b77e-f73c1bd4d466`, generation, четыре
приватных файла и прежняя нативная квитанция сохранились. Установка
получила ACK №2, в локальном outbox оставалась одна недоставленная
запись с исходным ключом `b29815e2ca3140208fd5f2ad489d96c8`.

Оба последующих POST выполнил Core 3.2.248. Это подтверждают
исполняемый файл в каталоге `versions/3.2.248`, селектор и WSS.
Gateway записал отчёт `7a587a22-3426-41ac-a63e-620a77881553`
в 23:55:36.975 UTC. Лабораторная обёртка завершила только процесс API
с кодом 79 до отправки первого HTTP 200. При выключенном API запись
в PostgreSQL уже была видна, `delivered_at` на клиенте оставался пустым.
После запуска API агент отправил тот же ключ и тот же результат
`failed/launcher_apply_failed` для целевого 3.2.206. Второй HTTP 200
прошёл в 23:55:50.316 UTC, клиент записал `delivered_at`.
В журнале клиента осталась одна запись, а PostgreSQL сохранил
тот же ID строки, статус и время terminal. Gateway принял свежую
WSS Core 3.2.248 `bdc625b4-c3e8-4515-ba9a-4e159e5d4459` на той же
карточке. Пауза была частью стенда для переноса отчёта. Отдельный
guard для повторного применения этим прогоном не проверялся.

Оба временных клона VM192 с выделенными дисками удалены. Проверено
отсутствие монтирования. Удалены выделенные API, worker, БД, IP
`192.0.2.148` и рабочие каталоги. Исходная VM132 сохранена, исходные
Gateway, PostgreSQL и worker VM142 активны. Подписанные артефакты
остались на рабочей станции.

Квитанции находятся в
`C:/endpoint-platform-wix-build/stab05-alt-native-248-ack-20261118`.
