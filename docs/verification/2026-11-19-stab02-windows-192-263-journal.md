# STAB-02 / STAB-15. SQLite Windows при переходе .192 ↔ .263

## Возврат между Windows .268 и основной версией .205

В четырёх отдельных процессах проверили модули из подписанных Windows Setup
.205 и .268 на одной временной SQLite. При возврате на .205 прежние записи
сохранились, но обработчик .205 не отправил сохранённый результат и оставил
очередь без изменений при получении ACK. После возврата .268 передала исходный
результат побайтово. Для начатой команды она сообщила неизвестный исход, для
зарезервированной — прерывание до старта. Три несовпадающих ACK сохранили
очередь, три соответствующих очистили её. Повторного вызова исполнителя на
.268 не было.

В отдельной копии БД при непосредственной повторной передаче команды старому
обработчику .205 тестовый счётчик сработал один раз. Решение Gateway, отправлять
ли команду повторно, в этом опыте не моделировалось. Испытание использовало
упакованный байткод, тестовый транспорт и синтетический исполнитель.

## Переход .192 ↔ .263

На Windows проверены модули Core из точных подписанных Setup 3.2.192 и 3.2.263. Для обеих версий проверены подписи Authenticode установщика и MSI, а также отпечаток сертификата издателя. SHA-256 Core после извлечения из вложенного архива совпал с проверенными значениями `0f0c3922…efc59` и `d2980dff…6bb79`. Проектные модули загружались только из упакованного байткода. Каждый из четырёх этапов выполнялся в отдельном процессе CPython 3.12 на временной синтетической SQLite с проверкой целостности. В клиентской проверке входящие команды и подтверждения передавал тестовый транспорт. Испытание с отключением питания и установкой пробной версии описано отдельно в [нативном прогоне .263](2026-11-19-stab15-windows-263-pre-native-recovery.md).

1. .192 создал SQLite schema 1 с таблицами legacy outbox и seen. .263 открыл её с тем же маркером, добавил inbox и reservations. Синтетический исполнитель вернул результат, который .263 записал и передал тестовому транспорту до ACK. Второй слот зафиксировал начало без результата, третий сохранил резервирование без старта.
2. Повторное открытие точным модулем .192 сохранило все строки и значения. Его обработчик проигнорировал matching result ACK. В этом Core нет штатного отправителя persistent pending результатов. На отдельной копии с синтетическим входящим command кадром тот же идентификатор дошёл до тестового исполнителя один раз и вернул результат через текущий транспорт. Таким образом, сохранение БД при rollback не даёт гарантии отсутствия повторного эффекта при фактической доставке команды в .192. Порядок выдачи на стороне Gateway проверен отдельно ниже.
3. После возврата к .263 штатное восстановление вернуло первоначальный JSON результата побайтно и сохранило все digest, device ID и deadline. Только слот после старта стал `AGENT_COMMAND_OUTCOME_UNKNOWN`, только он записан в legacy seen. Слот до старта стал `AGENT_COMMAND_INTERRUPTED_BEFORE_START`. Повторная доставка всех трёх в .263 послала результаты без нового вызова исполнителя. Неверные sequence и command ID оставили результаты pending, три точных ACK удалили их. После ACK команды не были исполнены или отправлены повторно.

Для повторной проверки скопируйте `replay.py` в отдельный временный каталог и запустите копию с `C:/endpoint-platform-wix-build/stability-ci-9891cc4afb3c/windows-env/Scripts/python.exe`. Скрипт сохраняет новую квитанцию рядом с собой.

## Доставка Gateway после смены версии клиента

На исходнике развёрнутого Gateway `44d96b5cce415e3886328c077499bee5f3b969ec` штатное ASGI-приложение приняло три последовательных соединения одного синтетического экземпляра устройства. В первом и третьем соединениях обе стороны согласовали журнал команд. Во втором тестовый клиент подключился без поддержки журнала, как .192. Приложение обрабатывало WebSocket-кадры в процессе теста с временной SQLite.

- Для команды `context.health.collect` Gateway выдал разрешение на старт и сохранил `running`. После смены сессии запись доставки осталась у исходной сессии. Новый клиент не получил эту команду при начальной диспетчеризации и в последующие 250 мс наблюдения.
- В контрольном случае команда оставалась в `delivered` без разрешения на старт. Gateway выдал тестовому клиенту без журнала исходный кадр с прежним идентификатором и сроком.
- После возврата клиента с журналом Gateway дважды подтвердил один результат с разными номерами кадров. В базе сохранилась одна успешная запись с прежним сроком команды.

Два сценария ASGI прошли. SHA-256 [квитанции ASGI](C:/endpoint-platform-wix-build/stab02-gateway-44d96-journal-legacy/gateway-mixed-asgi-receipt.json) — `f88accd69ad4da0a84ec9c9cb8767ab4053bb99a124d270abc1f1f480619180b`. Ещё четыре проверки покрыли уровень сервиса и согласование старта или отмены. SHA-256 [квитанции сервиса](C:/endpoint-platform-wix-build/stab02-gateway-44d96-journal-legacy/gateway-mixed-receipt.json) — `27b0fbf405f8665756c7d40db84405aa7277ab8f921c692e45ed99b3b9768134`. Сетевое обновление установленной .192 до .263 и последующую доставку из её собственного журнала ещё предстоит проверить на стенде.

Отдельная проверка `CommandService` на временной SQLite охватила потерю ACK **после фиксации результата и до подключения .192**. Сервис сохранил тестовый результат со статусом `failed` и сформировал ACK для кадра 17. При подключении клиента без журнала сервис не выдал ему эту команду. Когда клиент с журналом предъявил тот же результат в кадре 23, сервис подтвердил кадр 23. В базе осталась одна запись с исходным хешем результата. Сессии и потерю ACK моделировали внутри процесса. SHA-256 квитанции — `f5cfbf8e6a0e4360c07538da39b16dcaee8b4ebf50d54185af395564027b4ca7`. [Квитанция проверки](C:/endpoint-platform-wix-build/stab02-windows-downgrade-gateway/receipt.json)

## Проверка журнала в конечных пакетах Windows 3.2.264 и ALT 3.2.265

19 ноября из проверенных Windows Setup/MSI и ALT RPM извлекли исполняемые модули Core. В парах Windows .263 → .264 и ALT .261 → .265 из 13 выбранных модулей совпали исходники и упакованный байткод 12 модулей. Отличался модуль версии. Для Windows .253 → .264 дополнительно отличался `update_adapter`. Среди совпавших модулей были журнал, диспетчер команд и обработка подтверждений.

В локальной проверке с временной SQLite Windows .192 открыла базу .264 и сохранила ожидающие результаты. При возврате .264 доставила все три результата тестовому транспорту. Отдельная проверка извлечённых модулей ALT .265 повторно открыла SQLite в новом процессе. В обоих случаях ошибочные ACK оставили результаты в очереди, а три соответствующих ACK очистили её. Завершённая команда сохранила исходный результат. Команда с подтверждённым стартом получила неопределённый исход, зарезервированная — прерывание до старта. Повторного выполнения тестового действия не произошло.

Оба прогона использовали локальный Python и тестовый транспорт. Проверки с потерей питания и повторной доставкой команды через живую WSS на установленных .264 и .265 учитываются отдельно. ## Нативные проверки Windows 3.2.264 на сохранённой карточке

На изолированном клоне Windows 10 Enterprise Evaluation 19045 штатный Setup обновил .253 до .264 с кодом 0. Сохранились карточка и четыре файла идентичности. Сервер принял событие установки с ACK 4 и открыл новую WSS. Две разные команды `health_v1` проверили две точки отключения питания.

| Момент отключения | Что наблюдалось после холодного запуска |
| --- | --- |
| Gateway сохранил успешный результат и снимок, агент ожидал ACK результата | Через новую WSS агент передал тот же результат побайтно. В БД сохранились исходные единственные результат и снимок, в сетевом журнале — одна выдача команды. Только соответствующий ACK очистил очередь результата. |
| Агент записал начало команды, результат ещё отсутствовал | Сервер принял один результат ошибки `AGENT_COMMAND_OUTCOME_UNKNOWN` и ноль снимков. В журнале остались одна выдача команды и одно разрешение на запуск. После ACK локальная очередь была пуста. |

Суммы MSI и вложенного Core, четыре защищённых файла и ACK установки 4 совпали после обоих включений. ОС сообщала об истёкшем льготном периоде. В интервале измерений были зафиксированы только два запрошенных отключения. После проверки одноразовые VM254 и VM255, их диски и закрытый мост удалены. Исходный дамп лабораторной БД сохранил SHA-256.
