# STAB-02. Повтор результата после отключения питания Windows 3.2.253

Временную VM207 клонировали из выключенного снимка `setup253-positive-offline` VM206. Установленный MSI 3.2.253 совпал с подписанным артефактом по SHA-256 `801182e4abfeaa2eade65e0b94f00957fe4f2ed9359026419cc3f835d50a8fbc`. Установленный Core совпал с вложенным EXE подписанного Setup, SHA-256 `276da02be4349d48b78b7053cb9fea7bdb1377a4e09fdf5a27e42433d096ec20`, ревизия `0a1367ed83d2673ec047f1da5416e98b00050a8b`. Подпись и метка времени проверены у Setup и MSI. Вложенный Core идентифицирован по точным байтам.

Мост `vmbr207` соединял только VM207 и временный Gateway VM208. Gateway восстановил сохранённую положительную лабораторную БД с SHA-256 `443f1beb3f3909276ffb23d171b58672395d1cd0b84f70ed579540409be9e6b7` и использовал тот же лабораторный TLS. Гость проверил HTTPS по штатному имени и не имел маршрутов по умолчанию. Оригинальная VM206 оставалась выключенной, её Gateway находился на другом мосту. При загрузках клона его UTC сверяли с синхронизированным гипервизором до подключения NIC.

- Одна команда `health_v1` получила ID `cd8d0665-49ff-41c4-b9cb-c1f12c8d8120`. Gateway сохранил успешный результат `fabeb9b2-1338-441e-8a47-cf4fbb75fa30` с порядковым номером 18 и один снимок `42035b68-0a99-4190-9126-cf4b27b97759`. Испытательный слой собственного Gateway удержал `result_ack` только для этой команды. До отключения SQLite в режиме чтения показала одну завершённую запись inbox и один ожидающий результат outbox.
- В 11:26:54.628 UTC VM207 остановили через `qm stop`. После новой загрузки ранее сохранённый результат остался в outbox. На той же карточке установилась новая реальная WSS-сессия `938226ff-0320-40d5-8d9b-7b6d335ba445`. Gateway наблюдал одну выдачу команды и шесть отправок неизменной полезной нагрузки результата с SHA-256 `0792fd2496d9316ca53e70c5967e7aad7765b2347ac5bd1452505d9bd1566323`.
- В 11:29:40.982 UTC испытательный слой возобновил выдачу ACK. Штатный ACK подтвердил номер 2 последнего кадра в новой сессии. В PostgreSQL сохранились исходный номер 18, один результат и один снимок. В SQLite остались одна завершённая запись inbox, пустой outbox и ноль ожидающих разрешений на запуск. Четыре защищённых файла, выбранный Core и ACK установки 3 совпали.

VM207 и VM208, их диски, выделенный мост и временные копии лабораторных данных удалены. Хеш исходного сохранённого дампа совпал после уборки. Квитанции сохранены в `C:/endpoint-platform-wix-build/stab02-setup253-power-ack`, SHA-256 манифеста `6bfef52fd1878f6d81823fc3a0f73db82e3290ba4a9c2cd0f2913030c82ded19`.

## Отдельное отключение во время исполнения

На полном изолированном клоне VM213 проверили более раннюю границу с теми же байтами Core и MSI 3.2.253. Gateway выдал одну безвредную команду health. Перед отключением стенд удержал только дочерний worker этой команды. В 13:17:06.707786 UTC зафиксированы подтверждённый запуск и одна запись `running` в SQLite, ноль оставшихся разрешений на запуск и пустой outbox. Через 3,575 с гипервизор начал отключение питания.

После загрузки та же карточка открыла новую WSS в 13:17:53.519541 UTC. В журнале была одна выдача и один запуск команды. Агент сообщил `AGENT_COMMAND_OUTCOME_UNKNOWN`. PostgreSQL сохранил один результат со статусом failed и ноль снимков. После ACK локальная запись стала completed, outbox и очередь разрешений были пусты. Селектор, четыре защищённых файла и ACK 3 установки сохранились.

## Штатная остановка и запуск через SCM

На том же клоне после приёмки результата `Stop-Service` завершил отзывчивую службу за 1163 мс. Прежние launcher и Core завершились, служба перешла в Stopped с PID 0. После `Start-Service` появился один новый выбранный Core 3.2.253 с новой WSS на прежней карточке. Селектор, идентичность и ACK 3 сохранились.

Все 18 квитанций находятся в `C:/endpoint-platform-wix-build/stab02-setup253-power-during`. SHA-256 описи `receipts.sha256` — `9ac288e51b507be1cf54a3a95d5c541430979fb2acd1a62a33cbacb08e9cb0d3`. После проверки удалены VM213, VM214, их диски и выделенный мост.

## STAB-03. Принудительная остановка тестового дерева из двух процессов

На Windows в отдельный тестовый процесс загрузили реализацию координатора и Windows Job из `filServiceHost` подписанного MSI 3.2.253. Два обычных сценария управляющего канала завершились успешно. На отдельной фикстуре родитель и его потомок бездействовали и могли завершиться самостоятельно через 35 с. Проверяющий процесс заранее получил дескрипторы ожидания именно этих двух процессов.

После запроса остановки координатор отработал свой штатный предел 10 с, инициировал остановку собственного Job и вернул 0 через 10,070 с. Первая проверка, требовавшая немедленного сигнала обоих дескрипторов, завершилась ошибкой. Во втором инструментированном прогоне оба дескриптора через 0,02 мс после возврата всё ещё дали `WAIT_TIMEOUT`, а на следующем замере через 20,43 мс оба дали `WAIT_OBJECT_0`. Эти значения ограничивают наблюдавшееся окно. Сигнал дескриптора Windows подтверждает завершение соответствующего процесса. [Документация Microsoft](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process)

В проверенной реализации координатор завершает ожидание при нулевом счётчике активных процессов Job. Updater ориентируется на состояние службы SCM перед сменой версии. Два теста упакованного `filOfflineUpdater` подтвердили сохранение селектора при явном отказе SCM. Фактическая запись селектора в измеренном интервале не наблюдалась. Для строгого допуска остаётся подтвердить завершение предыдущего дерева перед записью селектора, в том числе после принудительной остановки.

Квитанции `C:/endpoint-platform-wix-build/stab03-setup253-package-check-20261118/host.json` и `updater.json` имеют SHA-256 `f78b0e26ac1cc188343c2a58eb3cf55f1c86d830138f868c2ea8fb3980d4da63` и `446098b5fe685d931d004bdb2c1410ef46c1ee6621ab7bebcf89861005e5d913`.
