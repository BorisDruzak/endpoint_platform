# Сохранность журнала команд на ALT 11.4

## Требование

Core должен сохранять на диске все изменения локального журнала команд до того, как их результатом сможет воспользоваться вызывающая сторона. Это относится к созданию и обновлению таблиц, приёму команды, резервированию и подтверждению старта, отмене, восстановлению, записи результата, удалению после точного ACK и очистке истории. Исполнитель запускается только после успешного сохранения отметки старта. Если запись завершилась ошибкой, вызывающая сторона получает ошибку этой операции.

## Реализация

На ALT каждое соединение, которое пишет журнал команд, устанавливает SQLite `synchronous=EXTRA` до начала транзакции. Для режима DELETE это требует синхронизации каталога при удалении rollback journal после commit. Существующие базы и очередь остаются читаемыми старым Core. Новый кандидат использует действующую схему и формат протокола. Область выпуска — ALT Workstation K 11.4. [Семантика SQLite](https://sqlite.org/pragma.html#pragma_synchronous)

## Основание и приёмка

На подписанной .266 до отключения наблюдался один исполнитель, одна запись `running`, ноль резервирований и ноль результатов. После загрузки для того же UUID пришёл `AGENT_COMMAND_INTERRUPTED_BEFORE_START`. Сохранён один результат и ноль снимков. В отдельном опыте на синтетической БД SQLite потеря записи каталога при FULL воспроизвела возврат резервирования. Причина исходного сбоя на диске ВМ остаётся предметом проверки. [Нативная квитанция](C:/endpoint-platform-wix-build/stab02-alt266-started-259/native-start-result.json) · [Синтетическая проверка](C:/endpoint-platform-wix-build/stab02-alt266-synthetic-vfs/verified.json)

Приёмка включает тест реального режима каждого пишущего соединения, ошибку сохранения до запуска, совместимость имеющейся базы и сравнение задержек записи в одном окружении. Подписанный кандидат проверяется на отдельной паре клиент/БД в закрытом контуре с уже разрешённой карточкой. После потери питания до старта ожидается `AGENT_COMMAND_INTERRUPTED_BEFORE_START`, после подтверждённого старта — `AGENT_COMMAND_OUTCOME_UNKNOWN`. После сохранения результата и потери ACK ожидается повторная доставка исходного результата. Для каждого сценария проверяются идентификаторы, число исполнений, число результатов на Gateway и очистка очереди после ACK. Итоги фиксируются отдельно по каждой достигнутой границе.
