### Verified defects and existing mechanisms

* runtime/application.py sets launcher_version=AGENT_VERSION. Fixed service_launcher.py does not pass its own compiled version.
* updater_service.py has file flush/fsync, atomic replacement and directory flushing. online_update_runtime.py uses temporary write_text plus replace; selector_migration.py fsyncs files but lacks directory flush. Terminal cleanup uses ordinary unlink.
* update_supervisor.py uses random.random, performs the first check immediately and owns short SCM retry separately from network backoff.
* corrective 3.2.81 acceptance explicitly documents manual ZIP→MSI receipt retirement after full payload/product/component verification.
* selector_migration.py preserves non-MSI selected cores but can advance MSI-owned selectors without comparing version order; newer-core preservation must cover every permitted origin.
* build-setup.ps1 already embeds MSI/manifest/CA/public config and supports signing/timestamp parameters. Production gate must require both Valid signature and timestamp.
* DeviceInstance currently stores only agent_version; PresenceService.open_session updates it from hello, and heartbeat updates that core version. UpdateTarget already stores the requested timestamps, and UpdateReport already stores report status/version/safe_code: expose those existing rows.
* StartupProofWriter uses write_text plus replace. update_adapter.py writes both endpoint_update_state.json and endpoint_update_reports.json the same weak way; its journal payloads are lists, so the shared writer must accept bounded JSON arrays as well as objects.
* runtime_identity.validate_runtime_executable checks semver, containment, reparse chain and executable existence; it does not itself hash the full runtime tree. Setup preservation/handoff must independently reuse or extend complete receipt/payload validation, rather than mistake path validation for byte identity.

## Approach

Extend the existing foundation/core split in place. This preserves the Universal Setup, update supervisor, canonical manifests and proven operation-bound WSS acceptance. A second version-reporting subsystem would duplicate launcher_version. Moving foundation upgrades into OTA would violate component ownership and legacy migration constraints. Neither alternative is selected.

## Version authority and compatibility

The fixed service host uses its compiled AGENT_VERSION, validates strict semver and passes --launcher-version with the canonical child command. Production child composition requires this value and cannot obtain it from environment or selected runtime version; development-only fallback is explicitly bounded. Test both core82/foundation82 and core83/foundation82. Inspect SCM/child privilege boundaries so an ordinary user cannot influence production invocation.

Persist nullable DeviceInstance.launcher_version on authenticated AgentHello through an additive migration. Heartbeats preserve it. Console device/update projections show core and foundation separately; freshness/unknown foundation must not be inferred from core. Version warnings are separate from WSS presence.

Add optional minimum_launcher_version to immutable build contract/storage/identity. Null means no additional requirement. Registration replay with changed minimum conflicts. Recommendation uses canonical latest device-instance foundation and fails closed for absent/invalid/too-old versions. Newer foundations permit lower-core rollback. Runtime/SDK/OpenAPI projections are updated where their actual contract exposes the field; Context7 must be consulted after determining pinned dependency versions.

Choose the latest canonical device instance deterministically, including a stable tie-breaker; never search backwards for an older non-null version when the latest foundation is unknown. Preserve legacy recommendation response compatibility when no minimum is declared; inspect strict frozen79 parsing before adding optional fields to a shared response base. Persisting foundation must not open WSS presence for a version-rejected connection.

## Durable state

Introduce one offline-safe durable_state module with no network imports. It writes bounded exact bytes via unique same-directory exclusive temporary file, validates reparse chains and protected roots, flushes file, atomically replaces, flushes directory and cleans temporary files. ACL publication follows each file's current owner. Do not broaden LocalService permissions to foundation files. durable_unlink flushes the containing directory when deletion is a correctness transition.

Migrate pending, update state/reports, startup attempt/confirmation, terminal outcome, current/previous selectors and MSI selector rollback metadata. A failure after replacement is an ambiguous durable transition, not permission to accept a candidate; startup reconciles validated journals/selectors. Corrupt/partial state degrades only the update lane. Acceptance still requires authenticated GatewayHello and operation-bound startup proof.

## Setup and provenance transaction

Before mutation inspect protected state and reject pending/verifying/terminal-report-pending as UPDATE_IN_PROGRESS. Recheck under a common protected exclusion boundary used by online publication/offline apply/Setup; a preflight-only check is insufficient to close the race. Stop only canonical managed Agent/Updater through reviewed paths before replacing their files; existing MSI lifecycle owns its companions.

Separate protected foundation MSI provenance from selected-core provenance. Compare version/source/tree/file count/every size and hash/product/component/receipt/selector before exact-runtime handoff. Archive superseded ZIP receipt, durably publish MSI core ownership and preserve restart/retry evidence. Same version with any identity mismatch returns PROVENANCE_CONFLICT. Never delete evidence to force READY.

Validated newer compatible core survives foundation upgrade. An approved older-core transition advances the selector transactionally with rollback. Same Setup rerun is idempotent and retains credentials/device/enrollment identity/CA/origin/ProgramData journals. Setup exits using existing stable behavior with new bounded reasons; successful final canonical preflight must be READY without hidden repair steps.

## Fleet preflight and disk safety

Extend read-only canonical preflight with bounded machine-readable core/foundation, MSI product/version, selected origin, WSS/update-lane state, pending/provenance, credential shape only, CA, disk and managed services. Emit distinct READY_FOR_SETUP_UPGRADE, ALREADY_CURRENT, UPDATE_IN_PROGRESS, PROVENANCE_CONFLICT, FOUNDATION_UNKNOWN, DISK_INSUFFICIENT, SERVICE_INVALID, CREDENTIAL_REPAIR_REQUIRED, TLS_REPAIR_REQUIRED.

Check target-volume space before download, before extraction and before foundation mutation. Budget compressed artifact, validated member total, pinned copy, retention and bounded margin without double counting existing retained allocations. Validate ZIP bounds before summing. Insufficient space preserves selector and known-good running Agent, emits bounded status and permits retry after capacity restoration.

## Scheduling and observability

Derive deterministic scheduling from device_id and purpose/attempt index only. Initial check 0–15 seconds; healthy interval about 300 seconds ±20%; capped network 5/10/20/40/80/160/300 and SCM 2/4/8/16/30 jitter. Authenticated success resets streak. One supervisor per root Agent lifetime; reconnect/rerun cannot create another.

Expose existing target assigned/requested/scheduled/updated/terminal timestamps and latest report status/version/safe_code/created_at without duplicate tables. Core newer than foundation is informational unless compatibility fails. HTTPS recovery does not open presence or deliver commands.
