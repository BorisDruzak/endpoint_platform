# Серверное автообновление Windows через полный Setup

> Для реализации использовать superpowers:executing-plans. Этот документ — план;
> он не включает массовое назначение обновлений или автоматическое повторение MSI.

**Результат проверки:** на 101.120 после полного удаления 158 и установки подлинной
Core/Foundation 156 переход доCore/Foundation 158 целиком прошёл через Endpoint.
Назначение fc126b5f-7abd-4b86-b787-856838dcdd7e, native exit 0, `applied`
2026-11-04T10:37:54.514968Z;182.356 с наблюдения, неизменные private-four и права,
проверенные службы и новое WSS. Подробности и ограничения:
[протокол](../../verification/2026-11-04-test120-clean156-full158.md).

**Цель:** после публикации и квалификации полного подписанного Setup сервер сам
создаёт устойчивые назначения подходящим устройствам по одной политике. После
включения политики на машине не требуются SSH, RDP, задачи администратора или ACL-правки.

**Текущая граница:** автоматическая доставка и исполнение одного назначения уже
работают. Выбор устройств, целевого выпуска, расписания и лимитов пока требует
действия оператора; постоянная серверная политика выбора ещё не реализована.
AUTO-кампания регистрации разрешает установку новых устройств и является отдельной
настройкой: она сама не назначает обновления существующим устройствам.

## Обязательные границы

- Полный Setup обновляет Foundation и Core. ZIP меняет только Core. Переходы 162
  и 155 в тесте — внутренние стадии подготовки клиента; целевой продукт остаётся 158.
  Нельзя выбирать целевой выпуск по максимальному номеру Core: 162 — служебный мост.
- Точный целевой артефакт — подписанный `EndpointAgentSetup-3.2.158-r3-x64.exe`,
  SHA256 3a603f2440bf501b85032e0defcdb8123efb5bdb31c1a7d4ed87433fcf7f7bb2.
  Одинаковая версия 158 у разных EXE не означает взаимозаменяемость ревизий.
- Пока доказан профиль чистой Foundation 156. Совместимый возврат — сохранённый
  Core 155; Core 157 требует Foundation 157. Старые 158 с проблемным владельцем updates
  не получили нового разрешения на массовое обновление по результату этого теста.
- Неизвестный native outcome удерживает эксклюзивный `recovery_required`.
  Запрещены автоматический повтор Setup, удаление журнала, переименование результата
  в успех или ручное снятие блокировки. Отмена допустима только до native start.
- Телеметрия по умолчанию включена; сохранены retention, idle и управление браузерами.
  Поддерживаются activity/browser, USB/print и browser upload/paste в audit-режиме.
  Неподдерживаемый removable-write не объявлять работающим.
- После SYSTEM-установки исходной 156 в существующей сессии test120 не было Tray и
  UserSensor. Обновление сохранило это состояние; sensor_count=0 не доказывает
  пользовательскую телеметрию. Проверка восстановления запущенного датчика уже была
  в отдельном тесте 03.11, но это другой исходный профиль. Перед широким запуском
  нужен объединённый тест чистой 156 с обычной пользовательской установкой и
  активным датчиком; все стадии после фиксации 156 — только через Endpoint.

## Изменяемые части

| Файл/область | Ответственность |
| --- | --- |
| `endpoint_server/setup_updates/models.py` + следующая Alembic migration | Политика автообновления, её версия, целевой полный выпуск, квалификация и решения по устройству |
| Новый `endpoint_server/setup_updates/policy.py` | Чистое вычисление eligible/blocked/waiting; без сетевых действий и MSI |
| Новый `endpoint_server/setup_updates/scheduler.py` | Ограниченные транзакции, идемпотентное создание canonical preparation/assignment |
| `endpoint_server/setup_updates/preparation.py` | Существующая цепочка bootstrap → совместимый возврат → Setup; сохраняет exclusive ownership |
| `endpoint_server/setup_updates/service.py`, `routes.py` | Проверки прав, просмотр, пауза, изменение версии политики, аудит |
| `endpoint_server/worker.py` | Вызов планировщика отдельной транзакцией без влияния сбоя одного устройства на другие |
| `webapp/src/FullSetupPage.tsx` + новый компонент политики | Одна политика, целевой выпуск, охват, окно, лимиты, причины ожидания и пауза |
| `tools/register_windows_setup_release.py`, `enrollment/default_campaign.py` | Уже реализованное включение новых опубликованных установщиков в единую AUTO-кампанию |

Новые внешние HTTP API/SDK-контракты не нужны для первого этапа: настройка остаётся
в Console admin boundary. Если позже появится внешний потребитель, добавить
канонический OpenAPI/SDK и проверить GitNexus group contracts отдельно.

## 1. Квалификация выпуска и готовность устройства

1. Сначала тесты `tests/server/test_setup_autoupdate_policy.py`: отсутствующая или
   устаревшая native-проверка, несовместимая Foundation, служебный bridge вместо
   продукта, неподписанный/неизвестный digest, активная Core/Setup операция,
   recovery hold, устаревшее соединение, повторное решение и откат версии политики.
2. Сохранить квалификацию по точной ревизии Setup и исходному профилю, с ссылкой на
   реальное exit 0/native/Core/private/service/WSS доказательство. Отделить готовность
   устройства, успешную установку и успешную пользовательскую телеметрию.
3. Первоначальный разрешённый профиль — проверенный 156→158. Для несовпадающего
   source вернуть ясный `blocked`/`waiting`; не снижать minimumFoundation и не
   применять чужую ACL-рецептуру. Неработающий старый stager требует отдельного
   исправления привилегированного канала и своей квалификации до включения в охват.
4. Для пользовательского теста запустить обычную установленную 156 с датчиком как
   часть её штатной установки, зафиксировать чистую 156 без observer и ACL-правок,
   затем доказать автоматическое сохранение/восстановление датчика на 158. Если
   требуется изменение продукта для запуска в уже существующей сессии, выпустить
   новый подписанный клиент с новым номером и протестировать его отдельно.

Проверка: unit-тесты матрицы и реальные native тесты; один `Running`, heartbeat,
observed version или APPLIED политики не заменяет эти проверки. Коммит:
`feat(updates): model qualified full Setup auto-update policy`.

## 2. Политика и устойчивый планировщик

1. Создать версионируемую политику: enabled/paused, точный SetupRelease FK,
   Windows scope, ограниченный список исходных профилей, maintenance window с
   явным часовым поясом, maxConcurrentNative, canary/fleet фаза. Новая политика
   начинается paused до назначения квалифицированного выпуска.
2. Решение уникально по device + версии политики + target digest. Повтор worker,
   перезапуск сервера или reconnect не создают второй native запуск. Сохранить
   последнюю проверенную причину blocked/waiting и источник решения.
3. Планировщик выбирает ограниченную порцию устройств, соблюдает общий порядок
   блокировок Build → Rollout/Target → Device и вызывает `request_setup`, а не
   пишет статусы напрямую. Лимит native запусков считается по реальным активным
   операциям, включая recovery holds, без гонки между worker-транзакциями.
4. Пауза останавливает новые назначения/ещё не начавшиеся стадии. Уже запущенная
   MSI завершается наблюдением; её неизвестный результат не освобождает слот.
5. Ошибка одного source не откатывает весь пакет. Безопасный код причины и аудит
   сохраняются без URL базы, токенов, личных данных и raw collector payload.

Проверка: реальный изолированный PostgreSQL — два планировщика, reconnect/restart,
два конкурирующих администратора, изменение политики, окна/DST, гонка на последнем
слоте, Core против Setup, отмена и recovery hold. Коммит:
`feat(updates): schedule idempotent full Setup assignments`.

## 3. Console и управление

1. Добавить чтение/изменение/паузу политики с существующими admin scopes, cookie
   и CSRF; изменение требует expected policy revision для защиты от lost update.
2. В Console показать обычную цель «158, полный Setup», охват, ближайшее окно,
   running/applied/blocked/recovery и причину ожидания. Служебные 162/155 остаются
   подробностями операции. Для ошибок ссылка на конкретную проверку и журнал.
3. Предпросмотр охвата read-only. Включение создаёт конкретную проверяемую политику;
   ручные назначения и автоматический worker используют одну state machine.
4. Не смешивать AUTO-регистрацию с обновлением. Единую кампанию сохранить:
   версии 63, 65, 79, 92, 149, 156, 156+setup.1, 158; новые trusted publication добавляются
   транзакционно, без расширения CIDR/квоты/срока и без новой кампании на версию.

Проверка: API scope/CSRF/conflict тесты, browser flow политики и ошибок, reload,
пауза во время native start, доступ обычного пользователя. Коммит:
`feat(console): manage full Setup auto-update policy`.

## 4. Приёмка и постепенный запуск

1. Dry run политики на реальной базе без назначений; проверить каждый source,
   исключить retired/offline/unknown/held и служебные build records.
2. Повторить 156→158 на test120 с активным обычным UserSensor. Никаких updater-
   задач, SSH, владельцев или ACL после принятия исходной 156. Документировать
   реальные native exit 0, Core/Foundation 158, private-four/file IDs/SDDL, службы,
   сохранённую сессию, новое WSS и не менее 180 с стабильной работы.
3. Проверить реальный post-install health, свежую policy APPLIED, advancing
   user_sensor_last_seen_at/activity intervals, browser extension при работающем
   поддерживаемом браузере, целевые USB/print/upload/paste события и WorkTime
   пользователя. Отсутствие действий не превращать в выдуманные security events.
4. Один canary → небольшая группа → последующие окна. Начальный native лимит 1;
   увеличение до 2 только после стабильного canary и проверки capacity. При первой
   новой native/provenance/private-file ошибке автоматически приостановить новые
   назначения этого профиля; не запускать бесконечные попытки.
5. Перед серверным deploy — clean exact commit, канонический Console archive,
   pinned production dependencies, backup/migration compatibility, capacity,
   strict TLS/HTTP/SSO и worker acceptance. Rollback сервера не повторяет native
   операции и не откатывает схему автоматически.

Проверка: fault-injection, прерывание питания/связи и рестарт worker во всех
существенных границах; неизвестный MSI результат остаётся hold. Отдельно проверить
производительность с реально работающим датчиком. Коммит:
`test(updates): qualify unattended full Setup policy rollout`.

Критерий завершения реализации — новые квалифицированные релизы и подходящие
устройства проходят весь цикл автоматически после включения политики, а остальные
имеют проверяемую причину ожидания. Массовый запуск до закрытия пользовательского
датчика и неподдержанных исходных профилей этим планом не разрешается.
