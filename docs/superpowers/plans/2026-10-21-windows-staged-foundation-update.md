# Staged Windows Foundation Update Implementation Plan

> **For agentic workers:** The user selected Native inline execution in this chat. Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Implementation remains in this chat.

**Goal:** Подготавливать Windows Foundation upgrade при работающем агенте, выполнять одну retention-копию, быстро переключать версию и автоматически восстанавливать прежнюю Foundation/Core при неудачной проверке работы.

**Architecture:** Существующий MSI owner сохраняет native transaction authority; отдельный application journal управляет online preparation, trial и post-commit rollback. Retention payload переносится в runtime каталог на том же NTFS-томе, а проверочный запуск разрешается только для точного кандидата. Сетевые credentials остаются исключительно у Agent; recovery owner запускается из защищённого signed cache.

**Tech Stack:** Python, существующие Windows dependency/build profiles, pywin32, PowerShell/C# owner, Windows Installer 5.0, WiX 4, PyInstaller 6.22.3 и hooks 2026.8; pytest и реальный Windows guest.

**Spec:** `docs/superpowers/specs/2026-10-21-windows-staged-foundation-update-design.md`, принята пользователем после коммита `f4962206a308990955d9be5526962eba1b2b2e2c`.

## Global Constraints

- Ветка `codex/windows-staged-foundation-update`; использовать уже прикреплённый изолированный worktree. Сохранить несвязанные изменения основного checkout. При выполнении прочитать `using-git-worktrees` и применимые `pc_agent/AGENTS.md` инструкции, не создавать второй worktree без необходимости.
- Подлинность исполняемых файлов проверяется до их запуска. Не отключать owner/package/session, подпись, hash, ACL, reparse, hardlink, TLS, native registration или enrollment guards.
- Длительная подготовка не должна останавливать связь и телеметрию старого агента. Неизменившиеся ZIP/retained деревья повторно не копируются.
- В успешном обновлении — одна retention-копия; promotion — перенос каталога на том же проверенном NTFS-томе. Дополнительная материализация разрешена только при фактическом rollback для совместимости старого helper.
- После handshake требуется 60 секунд стабильной работы с новым heartbeat; общий срок ожидания — 180 секунд. Не продлевать эти сроки на часы и не принимать один `SERVICE_RUNNING` за успех.
- Цели приёмки: до `accepted` — 10 минут для локально подготовленного пакета; до первого нового WSS handshake после остановки — 2 минуты. Reboot-required сценарии измеряются отдельно.
- Обязательные исходные состояния: подлинная legacy Foundation 3.2.79 и современная Foundation 3.2.120, включая вариант с отдельным Core 3.2.121. Невозможность безопасного rollback одного состояния оставляет задачу незавершённой.
- Сохранять device identity, credential bytes, CA/origin, outbox и исходные защищённые descriptors. Не создавать публичные dumps секретов/их digests. Изменения схемы данных должны допускать старую версию в rollback window.
- Только отдельный тестовый Windows guest: fresh preflight, отсутствие активного Setup/controller, новые operation IDs, сохранённые historical receipts. Не переиспользовать старые acceptance sequence и не изменять рабочую машину пользователя/production.
- Не пересобирать исторические releases под прежними именами. Свободный новый номер проверяется перед freeze. CI/source proof не заменяет signed installed acceptance.
- На каждой code-task: RED → GREEN, полный task diff, `git diff --check`, точное staging файлов и отдельный осмысленный Conventional Commit. Документация/CODEMAP обновляются вместе с изменённой границей.
- GitNexus MCP снова недоступен при подготовке плана (timeout); до final review повторить минимальный status/context/impact, если доступ восстановлен. Не запускать manual sync. Перед Windows API/library-dependent изменениями использовать Context7 с pinned версиями.

## Review Focus

1. Старый Core не знает новую reservation: старые mutex/OTA пути должны удерживать WSS живым и не менять выбранное дерево во время подготовки — Task 1/3, `test_legacy_core_cannot_race_online_prepare`.
2. Power loss между rename и записью `published`: recovery находит единственное точное дерево, не копирует его снова и не угадывает успех по наличию каталога — Task 2/6, `test_reset_between_promotion_and_receipt`.
3. Повтор старого proof, подмена attempt и перевод часов: кандидат не принимается; 60/180 секунд измеряются monotonic, а persisted timestamps служат дополнительной проверкой — Task 4, `test_trial_clock_rollback_and_replay`.
4. Health failure после native commit: восстанавливается настоящая старая Foundation registration, а несовместимый immutable helper не обходится фиктивным upgrade — Task 5, `test_post_commit_rollback_preserves_native_ownership`.
5. Нет интерактивного пользователя или он сменился: Session 0 не выдаётся за восстановленный Sensor/Tray, работа службы и companions проверяется раздельно — Task 6/8, `test_companion_session_changes_during_update`.

## File Structure and Shared Interfaces

Новые offline leaf modules не импортируют online adapter, aiohttp, build tooling или enrollment. Shared types определяются в указанных ниже модулях; последующие задачи используют эти имена. В перечнях Files имя без другого directory prefix означает точный путь под `pc_agent/platform/windows/`; имя Windows test без prefix — под `pc_agent/tests/windows/`.

| Файл | Ответственность |
| --- | --- |
| `pc_agent/platform/windows/staged_update_state.py` | Strict application journal, reservation, переходы и trial launch guard |
| `pc_agent/platform/windows/retained_storage.py` | Storage journal v2, единственная payload location, promotion и v1 rollback materialization |
| `pc_agent/platform/windows/staged_trial_proof.py` | Отдельные trial request/proof, свежие network lifecycle факты и health decision |
| `pc_agent/platform/windows/staged_foundation_rollback.py` | Проверенный reverse native plan и postconditions старой Foundation |
| `pc_agent/platform/windows/staged_recovery.py` | Ограниченный recovery entrypoint, task admission и восстановление application journal |
| Существующие owner/bridge/provenance/launcher/runtime/build files | Интеграция этих leaf interfaces, сохранение старых ABI и обычного Core OTA |
| `tools/canary/staged_windows_update.py` | Новый отдельный guest acceptance harness; старые Task13 tools/receipts не менять |

`StagedUpdateBinding` (frozen dataclass в `staged_update_state.py`) содержит `operation_id: str`, `old_release: dict[str, object]`, `new_release: dict[str, object]`, `selected_before: bytes`, `previous_before: bytes | None`, `selected_tree_sha256_before: str`, `previous_tree_sha256_before: str | None`, `candidate_version: str`, `candidate_source_revision: str`, `candidate_tree_sha256: str`. Release mappings проходят существующую exact package validation; binding digest вычисляется из однозначного canonical JSON, selectors кодируются hex. Исходные tree digests берутся из полной проверенной CoreInspection, а не выводятся из версии Foundation: выбранный Core может быть отдельным ZIP. Чужие keys/дубли JSON/неизвестные schemas отвергаются. Этот feature не меняет enrollment/outbox schema; их обратная совместимость проверяется настоящим запуском старого Core после rollback.

`StagedUpdateRecord` — frozen dataclass: `binding: StagedUpdateBinding`, `phase: str`, `sequence: int`, `attempt_id: str | None`, `owner: dict[str, object]`, `switched_at: datetime | None`, `safe_code: str | None`. Wire journal не больше 64 KiB, schema `endpoint_windows_staged_update_v1`; owner использует существующую strict PID/creation-time/image identity shape. Большие runtime manifests остаются в существующих bounded capture receipts.
