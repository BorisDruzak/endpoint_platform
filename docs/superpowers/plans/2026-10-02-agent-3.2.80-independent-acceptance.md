# Agent 3.2.80 Implementation and Independent Acceptance Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task by task in this chat. Preserve separate implementation and installed-service evidence.

**Goal:** Build immutable 3.2.80 and independently prove the installed 3.2.79 -> 3.2.80 recovery path on Windows canary 192.168.101.120.

**Architecture:** Extend the existing service-owned HTTPS supervisor and offline SCM updater. Server assignment owns release channel. An authenticated, per-device minimum-version gate rejects control sessions before presence becomes ONLINE while leaving device-authenticated update routes available. Candidate acceptance still requires authenticated WSS proof.

**Tech Stack:** Python; aiohttp 3.13.3; existing FastAPI/SQLAlchemy server; Windows LocalService/LocalSystem, SCM, WiX and PyInstaller.

**Spec:** `docs/superpowers/specs/2026-10-02-agent-3.2.80-independent-acceptance.md` (user-provided requirements; user explicitly requested building to these requirements).

## Review Focus

- Corrupt pending/journal state must disable update application without killing healthy WSS.
- Durable terminal report must settle before another recommendation, even after process restart.
- Legacy 3.2.79 client must parse a stable-channel response; test its exact packaged bytes rather than assuming server-only compatibility.
- Per-device minimum must reject before presence/session registration and must not affect other devices.
- Candidate and updater use actual MSI DACLs; source-process and injected triggers are insufficient.
