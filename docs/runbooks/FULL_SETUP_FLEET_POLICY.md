# Политика автоматического полного Setup Windows

Политика управляет существующими агентами. Кампания AUTO в разделе регистрации
разрешает первичную установку новых устройств и не включает эту политику.
Новая схема не создаёт политику, квалификацию или назначения. Состояние по
умолчанию — пауза; первоначальный лимит формы — одна цепочка.

## Управление в Console

1. Открыть **Релизы и обновления → Полный Setup**.
2. В блоке **Автообновление Windows полным Setup** выбрать точный полный выпуск
   по версии и имени EXE. Разные EXE одной версии имеют разные release UUID и digest.
   Служебные Core 162/163 и возврат Core 155 не являются целевым продуктом.
   У полного Setup нет потолка по номеру служебного Core: новый выпуск выбирается
   после собственной квалификации точного EXE и исходного профиля.
3. Выбрать **Все активные Windows-устройства** либо **Выбранная группа устройств**.
   Для группы отметить устройства; поиск устройств под блоком политики обновляет
   список, сохраняя уже выбранные UUID. Охват политики хранится на сервере.
4. Выбрать одну или две одновременные цепочки и указать причину.
5. Нажать **Предпросмотр охвата**. Предпросмотр не создаёт политику, решения или
   задания. Он показывает готовые, актуальные, ожидающие и заблокированные устройства,
   причины и свободные слоты. При более 500 устройствах явно показывает неполноту.
6. После проверки квалификации включить переключатель и нажать **Сохранить политику**.
   До сохранения переключатель является черновиком. После сохранения видны статус
   и версия политики; обновление страницы восстанавливает сохранённые поля.

Для паузы снять переключатель и сохранить. Пауза останавливает новые цепочки.
Уже начатая подготовка, MSI и наблюдение продолжаются через существующий контроллер.
Пауза не отменяет задания, не очищает журналы и не освобождает неизвестный native outcome.

Параллельное редактирование защищено expected revision. При конфликте черновик
сохраняется; проверить последний статус и использовать **Сбросить изменения**, затем
повторить осознанное изменение. Запись требует существующего права `updates:write`,
действующего admin-cookie и CSRF. Администратор без права записи может читать статус
и выполнять защищённый CSRF предпросмотр.

## Допуск и резервирование

Активное устройство — не retired, с точной `windows_amd64` из аутентифицированного
WSS hello, свежими совпадающими экземпляром и открытой Gateway-сессией (90 секунд).
После миграции неизвестная платформа ожидает нового подключения. Запись inventory
или давний heartbeat сами по себе не дают допуска.

Уже целевая или более новая Foundation пропускается без повторного Setup/понижения.
Неизвестный или неподдержанный source сохраняет безопасную причину. Первоначальная
приёмка относится к Foundation 156; Foundation 157/158 сами по себе не считаются
проверенными профилями. Другой source получает допуск только после собственного
реального canary с положительным native- и пользовательским доказательством.
Целевая версия выбирается из SetupRelease, без поиска максимального Core.

Проверка101.29 от05.11 выявила ограничение допуска по версии: существующая
Foundation156 с каталогом updates, принадлежащим Administrators, не смогла получить
bridge163. Старый Core156 переписывает DACL до скачивания, а служба LocalService
не имеет WRITE_DAC. На чистой156 тест120 каталог создавался самим агентом и этот
барьер не возник. Поэтому eligible в предпросмотре означает серверный допуск,
а не проверку исторических ACL и не гарантию установки. Конкретный bridge101.29
приостановлен до решения; общий fleet остаётся выключенным. Не чинить ACL вручную
под видом Endpoint-приёмки и не ослаблять защиту каталога.
См. [протокол101.29](../verification/2026-11-05-test29-endpoint-full158.md).

Слот резервируется на всю цепочку: подготовка → возврат → полный Setup → наблюдение.
Ручные полные Setup и recovery holds тоже занимают слот; подготовка и её native-задание
на одном устройстве считаются один раз. Независимые Core-only ZIP не занимают этот
глобальный лимит, но блокируют конкурентное назначение на том же устройстве.
При включённой политике ручное новое назначение Setup соблюдает тот же лимит.
На паузе явные одиночные canary оператора доступны через существующий контроллер.

Сервер хранит решение по версии политики, устройству и целевому digest. Перезапуск
worker/reconnect не создаёт второго задания; изменение политики не разрешает повтор
предыдущего неуспешного Setup. Новая ошибка/blocked/recovery собственных цепочек
автоматически ставит политику на паузу. Чужой ручной hold занимает слот без
автоматического изменения политики. Причины отображаются в последних решениях.

## Квалификация точного артефакта

Публикация EXE и включение его в AUTO не являются квалификацией fleet. Записать
квалификацию может оператор через каноническую серверную функцию в отдельной
maintenance-транзакции:

```python
from endpoint_server.setup_updates.policy import qualify_release

qualification = await qualify_release(
    session, release_id, evidence_assignment_id,
    actor=operator_id, request_id=request_id,
)
await session.commit()
```

Функция требует настоящий `applied` SetupAssignment не старше суток, совпадающий
release/MSI/source, native exit 0, private-four, службы, сохранённые companions,
180 секунд устойчивого наблюдения и `sensor_count > 0`. Требуются свежая готовая
presence клиента 1.0.5, новые WSS с целевыми Core/Foundation и свежий READY
`PolicySensorHealthCurrent` с `user_sensor_last_seen_at` не старше 150 секунд.

При создании назначения сервер сохраняет неизменяемые исходные Foundation/Core
и версию клиента из свежей квалифицированной presence. Исторические назначения
без этих полей не получают автоматическую квалификацию. Требуются исходный клиент
1.0.5, известная числовая Foundation не ниже156 и не выше целевого Setup, известный Core.

Если подготовка была нужна, требуется её завершение на том же устройстве/назначении
с применённым Core 163 `endpoint-windows-core-3.2.163-setup-client` и точным возвратом:
для Foundation 156 — Core 155 `endpoint-windows-core-3.2.155-setup-source-725739f`,
для157/158 — Core157 `endpoint-windows-core-3.2.157-setup-source`.
Старый bridge162 и отсутствие пользовательского датчика не проходят квалификацию.
Если действующий клиент1.0.5 уже был установлен, новый canary полного выпуска
может пройти напрямую без повторной подготовки. Например, реальное положительное
158→169 доказательство квалифицирует только источник158 для точного нового EXE.

Квалификация привязана к release UUID, SHA256, сохранённой исходной Foundation и UUID
доказательства, сохраняется с аудитом и действует 30 суток. Функция не включает
и не расширяет политику. До успешной квалификации UI не позволяет включить fleet;
одиночное назначение существующим контроллером остаётся доступно для canary.

## Реализация и границы

Console API: `GET/PUT /api/admin/setup-updates/fleet` и read-only
`POST /api/admin/setup-updates/fleet/preview`. Миграция: `0045_setup_fleet_policy`.
Worker использует отдельные ограниченные транзакции и PostgreSQL advisory lock;
назначение всегда проходит `request_setup`, с порядком Build → Device.

В этом этапе нет maintenance windows/DST или автоматической публикации/квалификации
нового выпуска. Предпросмотр ограничен 500 устройствами, последние решения — 100;
планировщик проходит весь сохранённый охват, а источник доказательств остаётся native
контроллер. Browser-тесты используют явные HTTP fixtures; PostgreSQL acceptance
выполняется только в отдельных disposable databases, не в производственной схеме.

Проверки реализации: `tests/server/test_setup_fleet_policy.py`,
`tests/server/test_setup_fleet_postgresql.py`, `tests/gateway/test_fleet_platform_presence.py`,
`webapp/src/SetupFleetPolicy.test.tsx`, `webapp/e2e/setup-fleet.spec.ts`.
Факт прохождения этих тестов не является native- или fleet-приёмкой.
